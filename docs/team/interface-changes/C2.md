## C2-IC-1 Baseline semantics of Linux inventory diffs (owner: B1; affects VM-002, CORR-002) — RESOLVED

B1's inventory (`collectors/src/extorq_collectors/linux/inventory.py`) emits no events for
the baseline snapshot of a category (verified in code, 2026-11-21). Original request:

**Request.** The first inventory snapshot of an asset (and any re-baseline after state
loss) must either emit **no** `persistence.systemd.*` / `persistence.cron.changed` events,
or emit them with `attributes.baseline = true`. VM-002 and CORR-002 ignore events with
`attributes.baseline = true`; without one of the two behaviours every pre-existing unit
would raise a VM-002 alert. (B3's macOS collector already treats the first scan as a
baseline without events; K8S-002 relies on the same `baseline` attribute for

file path / unit name), `attributes.sha256`, `previous_sha256`, `exec_start`,
`vendor_unit` on unit_created/modified; `resource.name` + `attributes.wanted_by` on
unit_enabled; auditd `file.audit.watch` with `attributes.audit_key = extorq_systemd` and
`resource.path` = the written path (exact match with the inventory path).

## C2-IC-3 What consumers can rely on (D1, D2, E)

* `alerts.service_ids` (0004) is populated from the evidence events' service references:
  the producing service (`events.service_id`, else `payload.service.service_id`) **and**
  the subject service (`attributes.subject_service_id`, B1 note 5: e.g. a VM-002 alert
  lists systemd and the persisted unit's own service), so the alert appears on both
  services' pages. A reference is dropped when the only valid `services` records for that
  id (id recomputes from `(asset_id, service_kind, service_key)`) belong to an unrelated
  asset (F-IC-6 consumer-side check).
* `InvestigationContext.services[].role` is `evidence` or `related`. When no trusted
  service record exists, `service_kind`, `category`, `adapter_support` and
  `monitoring_status` are the literal `unknown` (E maps it to "unrecognised"); a limitation
  explains why (record missing, or the reference points to another asset's service).
* `relationships` never include the alert's own evidence events; evidence membership is
  `evidence` / `timeline[].is_evidence`. Types: DIRECT / CANDIDATE / UNESTABLISHED with
  bases and strength (docs/correlation.md). `features.causation_established` is always
  `false`.
* `missing_telemetry`, `limitations` and `coverage[].note` contain only fixed phrases and
  validated identifiers (source types, rule ids, asset ids, IP addresses): safe to treat as
  trusted text. `relationships[].explanation` likewise contains no telemetry text (still
  rendered as text, never HTML).
* `load_latest_context` raises `ContextIntegrityError` when a stored body does not match its
  `input_hash` (never serves altered evidence); `ContextStoreError` on contract violations.
* `ContextBuilder(read_client)` works with `extorq_detect` and `extorq_api_ro`;
  `save_context` is insert-only (works with `extorq_api_writer`). `extorq_ai` cannot read
  `events`, so the AI worker can only load stored contexts (as E-IC-4 describes).
* `ContextBuilder.build` raises `AlertNotFound` (a `LookupError`) for unknown alerts and
  `ValueError` for malformed ids (API: 404 / 400 are appropriate).

## C2-IC-6 Evidence revalidation when a rule version changes (owner: lead; PROPOSAL, not implemented)

Alert evidence is append-only (`alert_evidence` rows, union-merged `evidence_event_ids` and
list features), so a rule fix cannot remove evidence an older version attached. Live case:
CORR-002 alert `b46da3805d1c6f17b6c1ed363b49a777` was created at 2026-11-21T15:05Z by v1.0.0
with an auditd `unlinkat` by `/usr/bin/rm` as persistence evidence; v1.2.0 no longer produces
it (`python -m extorq.detection.dryrun --rule CORR-002 --start 2026-11-21T14:00:00Z --end
2026-11-21T16:30:00Z` lists it under "stored evidence not produced by v1.2.0"), but the
stored alert keeps it and `features.persistence_writers` still contains `/usr/bin/rm`.
Proposal: contract `EvidenceRole.SUPERSEDED`; when the engine evaluates an existing alert
with a newer rule version over a window that covers the alert's whole span, it writes a new
alert version whose evidence array and features come from the current evaluation and
inserts `alert_evidence` rows with role `superseded` (and a later `added_at`, which the
`ReplacingMergeTree(added_at)` keyed by `(alert_id, event_id)` keeps) for the ids it no
longer produces. The old rows stay in the table history; the console shows superseded
evidence separately. Affects: lead (contract), D1/D2 (render the role), E (projection).
Until then the dry run explains the delta, and analysts can record their verdict in
`analyst_state`.
