## D1-IC-1 Per-deployment Grafana `secret_key` (owner: A; affects D1)

**What.** `make bootstrap` generates `var/secrets/grafana_secret_key` (0600, >= 32 random
bytes, same generator as the other secrets); `compose.yaml` adds a file secret
`grafana_secret_key` to the `grafana` service and the environment variable
`GF_SECURITY_SECRET_KEY__FILE: /run/secrets/grafana_secret_key`.

**Why.** Grafana encrypts stored secrets (here: the provisioned ClickHouse password of
`extorq_grafana`) with keys protected by `secret_key`. Without it Grafana uses its public
built-in default, so a copy of the `grafana-data` volume reveals the datasource password.
Today the impact is bounded (the same password is in `var/secrets`, and the identity is
read-only), but it is a cheap defence in depth.

**Rollout note.** Set it before the first start, or recreate the `grafana-data` volume
(no state of value is stored there: datasource and dashboards are provisioned from the
image at every start). No D1 file changes are needed.

## D1-IC-3 Findings view `service_id` (owner: C3; informational)

When `0005_findings_services.sql` adds `service_id` to `v_findings_current`, nothing in the
API breaks: it attributes findings through `finding_observations.service_id` (latest non-null
attribution per finding) and filters with `finding_id IN (SELECT ... WHERE service_id = ?)`.
Please keep `finding_observations.service_id` populated (it is the source of truth either way).
