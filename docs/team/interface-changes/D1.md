## D1-IC-1 Per-deployment Grafana `secret_key` (owner: A; affects D1)

**What.** `make bootstrap` generates `var/secrets/grafana_secret_key` (0600, >= 32 random
bytes, same generator as the other secrets); `compose.yaml` adds a file secret
`grafana_secret_key` to the `grafana` service and the environment variable
`GF_SECURITY_SECRET_KEY__FILE: /run/secrets/grafana_secret_key`.

**Why.** Grafana encrypts stored secrets (here: the provisioned ClickHouse password of
`extorq_grafana`) with keys protected by `secret_key`. Without it Grafana uses its public
built-in default, so a copy of the `grafana-data` volume reveals the datasource password.
Today the impact is bounded (the same password is in `var/secrets`, and the identity is
read-only), but it is a cheap defence in depth.

**Rollout note.** Set it before the first start, or recreate the `grafana-data` volume
(no state of value is stored there: datasource and dashboards are provisioned from the
image at every start). No D1 file changes are needed.

## Session 3 (2026-11-21 UTC) additions

### D1-IC-5 Additive API fields (informational; D2 already consumes them)
`AssetListItem.collectors_inherited` (and therefore `AssetRecord`): collectors that cover the
asset through an ancestor (a Kubernetes node is covered by its cluster's collectors; asset
coverage now uses the same ancestor rule as service coverage). `AssetServicesResponse.hosted`
+ `hosted_truncated`: services of an ancestor asset with instances on the asset (a node's
Pods/containers grouped by cluster workload). OpenAPI regenerated; no field removed or
retyped.

### D1-IC-6 F-19, API part implemented (owner F: re-check; owner A: informational)
Service views are scoped to the service's own asset subtree (instances, per-source telemetry,
auth activity, recent events, `GET /events?service_id=`), and a stored service row is used
only when its id matches `identity.service_id(asset_id, kind, key)`. Remaining gap outside
D1: the gateway binds `service` and `service_instance` ids, but not `SecurityEvent.service`
(an event of asset X may still carry asset Y's `service_id`). The API now hides such events
from Y's views, but the detector may still copy that id into `alerts.service_ids` of X's
alert. Suggestion (A or C2, not urgent): quarantine or strip an event's `service` ref whose
`service_id` is not a service of the event's asset (or a descendant), or let the detector
ignore foreign service ids.

### D1-IC-7 ClickHouse quota of `extorq_api_ro` (owner A / lead; informational)
`extorq_api_quota` allows 1200 queries per minute for ALL API users together (compose `api`,
dev APIs, live tests). One console page costs about 10-20 queries. An unpaced smoke run
exceeded it (1434/1200) at ~20:31 UTC and every API user got errors until the minute ended.
D changed the API to answer 429 + `Retry-After: 30` on QUOTA_EXCEEDED (the console retries
502/503/504 only) and paced the smoke and live tests. No quota change is requested for the
demo (one analyst stays far below it); keep load tests and parallel agent checks paced.

### D1-IC-8 Kubernetes service instances not refreshed (owner B2; observed, not fixed by D)

## Session 4 (2026-11-22, agent API-DATA acting for D1 + A)

### D1-IC-9 Asset/collector lifecycle and retired assets (informational; D2/UI-4, F)
Additive API fields (OpenAPI regenerated; nothing removed or retyped): `lifecycle_state`,
`last_observed_at`, `lifecycle_reason` on assets; `lifecycle_state`, `self_test` on
collectors; `retired_excluded`, `assets_retired`, `collectors_retired`, `OverviewResponse.lifecycle`;
`include_retired` on `GET /assets`, `/overview`, `/health`. Behaviour change: by default
retired assets (no collector reporting for them and not observed within 24 h) and their
collectors are left out of the asset list and of the overview/health rollups (counted and
named, never deleted); open alerts are never filtered. SDK heartbeat self-tests (A-IC-1) no
longer count as asset coverage. Rules: `docs/api/README.md` "Asset and collector lifecycle".
F: `docs/known-limitations.md` may want the two limitations listed there (a collector removed
from configuration while another still reports for its asset stays `stale` until its health
rows expire; a node removed from a cluster stays `stale` while the cluster collector reports).

### D1-IC-10 extorq_api_ro quota 6000/min (migration 0007) + 15 s response cache (F, D2/UI, A)
`infra/clickhouse/migrations/0007_api_quota.sql` (applied live 2026-11-22 06:55 UTC) raises
`extorq_api_quota` from 1200 to 6000 queries per minute; errors (300), result rows, read rows
and execution time are restated unchanged (ALTER QUOTA replaces every limit of an interval;
verified on ClickHouse 26.8). The API also caches its aggregate responses for 15 s
(`EXTORQ_API_CACHE_TTL_SECONDS`), and `/health` answers 429 instead of "storage unreachable"
when the quota is exhausted. Measured: a paced console smoke run peaked at 222-296 queries per
minute. Docs that still say 1200 (owners update them): `docs/security.md` line on
`extorq_api_ro` + F-29 status (F), `docs/operations.md` troubleshooting row and
`docs/demo-runbook.md` 2.2 (F), `frontend/AGENTS.md` smoke-pacing paragraph and the comment in
`frontend/scripts/smoke.mjs` (D2/UI). Pacing stays good practice: the quota is still shared.
