# D2 (security console) interface requests

Last updated: 2026-11-21 (session 2: status notes added per section)

## 1. Console secrets and compose wiring (for A: bootstrap + compose.yaml)

The console (`frontend/`) reads every secret from a file path given in an environment
variable; values are never logged or sent to the browser. It needs:

| Env var (frontend container) | Proposed host file (`make bootstrap`, 0600) | Content |
|---|---|---|
| `EXTORQ_API_TOKEN_FILE` | `var/secrets/api_service_token` (same file D1's API reads via `EXTORQ_API_SERVICE_TOKEN_FILE`) | random token, >= 32 chars |
| `EXTORQ_ANALYST_PASSWORD_FILE` | `var/secrets/console/analyst_password` | random password, >= 12 chars (console refuses shorter) |
| `EXTORQ_VIEWER_PASSWORD_FILE` | `var/secrets/console/viewer_password` | random password, >= 12 chars |
| `EXTORQ_SESSION_SECRET_FILE` | `var/secrets/console/session_secret` | random string, >= 32 chars (HS256 cookie signing key) |

Non-secret settings: `EXTORQ_API_BASE_URL=http://api:8000` (required), optional
`EXTORQ_ANALYST_USERNAME` / `EXTORQ_VIEWER_USERNAME` (defaults `analyst` / `viewer`),
`EXTORQ_HTTPS=auto|true|false` (default auto; the compose console is plain HTTP on loopback,
so the cookie is not `Secure` there; set `true` behind TLS).

Proposed `compose.yaml` service (A owns the file):

```yaml
frontend:
  build: { context: ./frontend }
  environment:
    EXTORQ_API_BASE_URL: http://api:8000
    EXTORQ_API_TOKEN_FILE: /run/secrets/api_service_token
    EXTORQ_ANALYST_PASSWORD_FILE: /run/secrets/console_analyst_password
    EXTORQ_VIEWER_PASSWORD_FILE: /run/secrets/console_viewer_password
    EXTORQ_SESSION_SECRET_FILE: /run/secrets/console_session_secret
  secrets: [api_service_token, console_analyst_password, console_viewer_password, console_session_secret]
  ports: ["127.0.0.1:3000:3000"]
  networks: [edge]
  read_only: true
  tmpfs: ["/tmp", "/app/.next/cache"]
  cap_drop: [ALL]
  security_opt: ["no-new-privileges:true"]
  healthcheck:
    test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/healthz').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
    interval: 15s
    timeout: 5s
    retries: 5
  depends_on: { api: { condition: service_started } }
```

The image runs as uid 1001 (`nextjs`); the mounted secret files must be readable by that
uid (see the verification note in `docs/team/status/D2.md`).

**Status (session 2):** A wired the service into `compose.yaml` (profile `full`) with host files
`var/secrets/api_service_token`, `analyst_password`, `viewer_password`,
`frontend_session_secret`; that matches what the console reads. Verified by D2 with an
equivalent throwaway container (`extorq-d2-console-test`, removed): `--read-only`, tmpfs
`/tmp` and `/app/.next/cache` (uid 1001), `--cap-drop ALL`, `no-new-privileges`, uid 1001, the
four files bind-mounted read-only under `/run/secrets/`. On Docker Desktop (virtiofs) the 0600
host files are readable by uid 1001; the healthcheck reports healthy and the smoke test passes.
The compose service itself (`docker compose --profile full up frontend`) was not started by D2
(it depends on A's `api` service). Nothing further is requested from A.

## 2. Analyst API (D1)

No change required: the console consumes `docs/api/openapi.json` as published (generated
types in `frontend/src/lib/api/openapi.d.ts`; `frontend/src/lib/api/contract-check.ts` fails
`pnpm typecheck` if a field the console uses is removed or retyped). Notes for D1:

- Asset ids are sent percent-encoded as one path segment (`/api/v1/assets/github%3Aowner%2Frepo`);
  this relies on the `{asset_id:path}` route, which is already in place.
- `POST /alerts/{id}/summary` is called without a body and with a 90 s timeout
  (`EXTORQ_SUMMARY_TIMEOUT_MS`); 409/429/503 `detail` strings are shown to the analyst.
- `POST /alerts/{id}/state` sends `expected_updated_at` (from `analyst_state.updated_at`) so a
  concurrent change produces 409 rather than a silent overwrite.

## 3. Service drill-down (D1; PLAN §10, contracts 1.1) — what the console consumes

**Status (session 2): satisfied.** D1 published the endpoints (`AssetServicesResponse`,
`ServiceListResponse`, `ServiceDetailResponse`, `services_summary`, `child_assets`,
`service_coverage`, the additive event/alert/finding fields). The console uses D1's shapes
(regenerated `openapi.d.ts`, contract check extended) and shows D1's effective
`coverage_state` with `coverage_reasons`. The original request is kept below for the record.

Added 2026-11-21 (session 2). The console builds the drill-down
Asset → Services/Workloads → Telemetry → Findings → Alerts → Investigation against the
contract field names in `backend/src/extorq/contracts/service.py`; until D1 publishes the
new paths in `docs/api/openapi.json` it uses provisional zod schemas with exactly those
names (`frontend/src/lib/api/schemas.ts`, section "Services") and shows an explicit
"service inventory API not available" state on 404. Requests (field names = contract names):

1. `GET /api/v1/assets/{asset_id}/services` → `{asset_id, items: ServiceListItem[], coverage:
   {discovered, adapter_implemented, monitored, degraded, unmonitored, planned, unsupported},
   page}` where `ServiceListItem` = every `Service` field (incl. `endpoints[]` with
   `exposure`, `attribution`, `attribution_basis`; `coverage_note`; `telemetry_sources`;
   `present`) plus derived `open_alerts`, `open_findings` (nullable when not derivable).
   Tombstoned services (`present=false`) included and flagged, not dropped.
2. `GET /api/v1/services/{service_id}` → `{service: ServiceListItem, asset: AssetBrief,
   instances: ServiceInstance[] (incl. tombstones flagged), telemetry: per source type
   {source_type, collector_id, status, last_success_at, last_event_at, lag_seconds, stale,
   events_24h}, events: EventListItem[] (recent, service_id match), findings: FindingItem[],
   alerts: AlertListItem[] (service_ids contains it)}`.
3. `GET /api/v1/services?asset_id=&service_kind=&monitoring_status=&adapter_support=` → list
   across assets (same item shape).
4. Additive fields on existing models: `AlertListItem/AlertRecord.service_ids`,
   `EventListItem.{service_id, service_name, service_instance_id, adapter_id, k8s_container_id}`,
   `FindingItem.service_id`, `ContextResponse.context.{services, related_assets}` and
   `EventSummary.{service_id, service_name}` (contract `InvestigationContext` 1.1).
5. Kubernetes: workloads (`k8s_workload`) and logical Kubernetes Services (`k8s_service`)
   belong to the cluster asset; nodes are assets (`kubernetes_node`, parent = cluster);
   Pods/containers are instances (`instance.asset_id` = node). If cheap, a
   `?instance_asset_id=` filter (instances running on a node) lets the node page list its Pods.

The console tolerates unknown enum values (new asset types, service kinds, categories) by
rendering the raw token instead of failing validation.

Routing note (verified against the running API, 2026-11-21): today
`GET /api/v1/assets/linux%3Alab-vm-01/services` is captured by the existing
`/assets/{asset_id:path}` route and answers `404 asset not found` (asset id
`linux:lab-vm-01/services`). Register `/assets/{asset_id:path}/services` before the
catch-all asset route (node ids such as `k8s:extorq-lab/node/<name>` contain `/`).
