## 3. Requests to A (platform) and the lead — PROPOSALS

### 3.1 SDK config secret check rejects boolean `*_token` settings (A)

`extorq_collectors.sdk.config.CollectorConfig._no_secret_values` runs `redact_text` over the
YAML dump of `settings`; the `secret_assignment` rule matches any key ending in `token`
followed by a value, so `allow_gh_cli_token: true` (a boolean) is rejected as "appears to
contain a secret". Proposal: only inspect string values (booleans/numbers cannot be
secrets), e.g. walk the mapping and run `redact_text(f"{key}: {value}")` for `str` values
only. Workaround in place: the GitHub collector also accepts the YAML key
`gh_cli_token_fallback`. The same rule also rewrote my health warning text
(`allow_gh_cli_token=true` -> `[REDACTED:secret]`); I rephrased the warning.

### 3.2 Gateway acceptance window (400 d) exceeds the events TTL (90 d) (A + lead)

PLAN 5.1: events older than 400 days are quarantined; `0001_core_tables.sql`:
`events ... TTL toDateTime(event_time) + INTERVAL 90 DAY`. Events 90-400 days old are
accepted with 202 and then removed by the TTL, so the producer believes they were stored.
Observed live 2026-11-21: three `github.commit.observed` events of
`actions/hello-world-javascript-action` (genuine push time 2026-02-18) were accepted
(collector outbox drained, 0 quarantined) and are absent from `extorq.events`.
Proposal: quarantine events older than the events retention with reason
`older_than_retention` (visible in `ingest_quarantine`), or align the TTL with the
acceptance window. Not a demo blocker (the lab repository is new).

### 3.3 Let a collector mark a successful cycle as DEGRADED (A)

The runner sets `ok` whenever `collect()` returns. The GitHub collector can finish a cycle
with partial results (one of several repositories failed, rate limited mid-cycle, a broad
gh CLI token in use). Proposal: `ctx.degraded(reason: str)` (or a `health_status_hint`)
that the runner maps to `HealthStatus.DEGRADED` with the reason in `last_error`. Until then
the GitHub collector reports these in `details.errors` / `details.warnings`.

## 7. Session 3: fail-closed workflow analysis and per-commit isolation (consumers: **C2**, D1/D2, F)

Additive attribute changes only; event types, identities and existing attributes are

### 7.1 `github.workflow.modified` when a workflow cannot be analysed (`analysis="lexical_fallback"`)

Before: a workflow version that existed but could not be parsed (larger than 512 KiB, more
than 100 YAML aliases or 50 000 nodes, invalid YAML, duplicate keys, not a mapping) was treated
as absent, so an escalation hidden that way produced no GH-001 input. Now the collector
reads the file as a bounded prefix (4 MiB, raw media type) and, when either version is
unanalysable, compares BOTH versions with a bounded lexical scan
(`workflow.lexical_scan`). The scan finds, outside full-line comments: `write-all`;
`<write-capable scope>: write` pairs in block, flow or JSON style (tags, explicit keys,
scalar anchors/aliases and `\x`/`\u` escapes resolved); the privileged triggers
`pull_request_target`, `workflow_run`, `issue_comment` (not when only named inside a
one-line `${{ }}` expression or as a property such as `github.event.workflow_run`); checkout
of untrusted code (`ref:` / `repository:` using the PR / workflow_run head expressions,
`gh pr checkout`, `git fetch|checkout ... pull/${{`, `allow-unsafe-pr-checkout`). It cannot
tell which job a declaration belongs to, so it over-approximates (safe direction).

Attributes in this mode (all keys still present):

| Attribute | Value in lexical mode |
|---|---|
| `analysis` | `"lexical_fallback"` (`"structured"` otherwise; new key on every event) |
| `effective_permissions_unknown` | always `true` |
| `write_all_added` | `write-all` in the new version and not in the old one |
| `added_write_scopes`, `write_scopes_before/after` | declared write scopes (write-all = every write-capable scope; with repo default `write` and no `permissions` key at all, the permissive default) |
| `triggers_before/after/added/removed`, `dangerous_triggers_added` | only the privileged triggers above (the lexical scan looks for nothing else) |
| `untrusted_checkout_added` | privileged trigger + untrusted checkout in the new version and not in the old |
| `permissions_before/after` | structured rendering for a parsed version; `unparseable;lexical=<write-all\|write:<scopes>\|no write scope detected\|no permissions key>[;truncated]` for an unparseable one |
| `parse_error_before/after` | the parser error of the unparseable version(s) (non-empty) |
| `lexical_truncated` | `true` when a version was larger than the 4 MiB scan bound (rest not examined); `null` in structured mode |
| `lexical_evidence` | fixed labels of the untrusted-checkout evidence (no attacker text) |
| `unpinned_actions_added/after`, `script_injection_added`, `secrets_inherit_added` | `null` = not analysed (never "none found") |
| `risk_flags` | adds `analysis_lexical_fallback`, `effective_permissions_unknown`, `workflow_unparseable` / `baseline_unparseable`, `lexical_scan_truncated`, `workflow_lexical_unavailable` / `baseline_lexical_unavailable` |
| `workflow_sha256_after/before` | `null` when only a prefix was read (a prefix hash is not the file hash) |
| `raw` | `diff omitted: ... exceeds 524288 bytes (analysed lexically)` when a version is larger than the YAML bound (no superlinear diff of huge text); the normal redacted diff otherwise |

### 7.2 Per-commit isolation (`gap_reason="commit_unavailable"`)

A commit whose detail or workflow content cannot be read no longer blinds the repository
(before: the error aborted the poll at the same checkpoint every cycle, and runs, posture
and security-alert phases never ran again). Now:

* 401 and rate limits still propagate (they affect every request).
* Permanent errors (4xx such as 404/409/422 "diff taking too long", 403, oversized or
  malformed responses): `extorq.collector.gap_detected` at once and the branch checkpoint
  moves past the commit. Event: `github.{repository, ref, commit_sha}`;
  `attributes.{gap_reason="commit_unavailable", commit_sha, branch, http_status (int|null),
  error_type, endpoint, attempts, transient}`; identity `gap:commit_unavailable:<sha>`;
  message names the repository, the short commit and `HTTP <status>`.
* Transient errors (5xx/408/network after the client's 3 in-request attempts): the commit
  goes into a bounded retry set in the checkpoint (max 32 commits) and the branch moves on;
  it is retried once per later poll with its genuine push time and pusher; after 3 polls it
  becomes the same gap event (`transient=true`). A commit's records are all-or-nothing.
* A failure to LIST a branch's commits (compare API) keeps that branch's checkpoint (retried
  next poll) while other branches and the runs / posture / alerts phases still run; the
  poll reports `incomplete` and the cycle health says "no repository was polled completely".

Consumers: D1/D2 may surface `commit_unavailable` gaps on the repository timeline; GH-001
cannot fire for a skipped commit, which is exactly what the gap event records.

### 7.3 Posture and inventory

`github.workflow.unparseable` findings now carry the lexical indicators in `evidence` and
`attributes.{analysis, lexical_write_all, lexical_write_scopes, lexical_privileged_triggers,
lexical_untrusted_checkout, lexical_truncated}`; severity `high` (write-all or privileged
trigger + untrusted checkout), `medium` (write scopes or privileged triggers), else `low`.
`github_workflow` inventory items gain `analysis` and the same `lexical_*` keys for
unparseable files. Oversized blobs are fetched as a 4 MiB prefix instead of being skipped.
