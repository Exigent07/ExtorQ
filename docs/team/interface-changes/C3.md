## C3-IC-3 Consumers of the findings views (owners: D1, D2, Grafana)

* After C3-IC-1: `v_findings_current.service_id` = service of the most recent observation
  (NULL when not attributable). Use it for `GET /api/v1/services/{service_id}` findings,
  filtering by the service's asset as well (`WHERE asset_id = {asset:String} AND
  service_id = {sid:String}`, cf. F-IC-6: ids are computable from public facts, so a
  producer could otherwise attach findings to another asset's service). The scanner always
  derives the id from the finding's own asset; today only Linux OS-package findings are
  attributed (evidence-gated, `attributes.service_attribution = inferred:package-ships-unit`).
* OS-package vulnerabilities are one finding per (CVE, source package): `package_name` is
  the SOURCE package (e.g. `linux`, `openssh`, `glibc`) and `installed_version` the source
  version; the affected binary packages are in `finding_observations.attributes`
  (`binary_packages`, `package_basis = source`). Language packages are per package.
* Scan history: `v_scan_runs_current` (`effective_status`, coverage JSON, `error`). Image
  scans keep `image_ref`, `image_id`, `repo_digests` in `attributes`.

## C3-IC-4 Dispatch output relied upon (owner: B1)

The scanner uses `extorq_collectors.linux.ssh.SSHDispatchClient` with defaults (no
`config/collectors/linux.yaml` ssh block needed) and two dispatch commands:
`packages` (schema `extorq.linux.packages.v1`, as documented in interface-changes/B1.md) and
`inventory` (only `systemd_units[].{name, unit_dir, role, kind, symlink_target, exists}`).
Please keep these fields stable. Host-service ids are computed as
`identity.service_id(asset_id, "host_service", <systemd unit name>)`, matching
`ServiceCandidate.service_key` (unit name) of the shared services interface.
