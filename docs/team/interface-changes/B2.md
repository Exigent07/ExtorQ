## B2-IC-2 Redaction false positive on JSON booleans (owner: A, informational)

`redact_text('{"automount_sa_token":false}')` -> `[REDACTED:secret]`. A boolean or number is
never a credential; consider exempting JSON `true|false|null|<number>` values from the
assignment rule. B2 worked around it (B2-IC-1); other producers that put JSON in attributes may
hit the same corruption.

## B2-IC-3 Canonical container id (owner: lead, docstring only)

`KubernetesInfo.container_id` documents the example `containerd://<64 hex>`. The OTel
k8s_attributes processor reports the BARE id (64 hex, no runtime prefix) while the API reports
`containerd://<id>`. B2 uses the bare id everywhere (events `kubernetes.container_id` /
`events.k8s_container_id`, container `ServiceInstance.instance_key` and `.container_id`) and
keeps the runtime in `ServiceInstance.attributes.runtime`, so the two paths join without string
manipulation (verified live: 186/186 kindnet log events join their container instance).
Proposal: change the docstring example to "bare runtime container id (64 hex); runtime prefix
dropped". No code change.

## B2-IC-4 Kubernetes service identities (consumers: C2, D1, D2, E) - IMPLEMENTED

All ids come from `extorq.ingest.otlp_k8s` helpers (shared by the OTLP normaliser and the
inventory collector):

| record | id | key |
|---|---|---|
| node asset | `k8s:extorq-lab/node/<node>` (AssetType `kubernetes_node`, parent `k8s:extorq-lab`) | |
| workload Service (`k8s_workload`) | `identity.service_id("k8s:extorq-lab", "k8s_workload", key)` | `<ns>/<Kind>/<name>`; Kind = top-level controller (Deployment, DaemonSet, StatefulSet, CronJob, standalone ReplicaSet/Job) or `Pod` for bare and static pods |
| Kubernetes Service (`k8s_service`) | `identity.service_id("k8s:extorq-lab", "k8s_service", key)` | `<ns>/<name>` |
| Pod instance | `identity.instance_id(service_id, "pod", key)` | pod UID; for static pods the kubelet config hash (`kubernetes.io/config.hash`, = UID in node log paths) |
| container instance | `identity.instance_id(service_id, "container", key)` | bare container id; parent = pod instance |

Service `name` is `<ns>/<name>` for both kinds (distinguish by `service_kind`). Events:
container logs -> workload service + container instance (pod instance when no container id);
lab-portal app events: adapter `webapp-json`; other container lines: `k8s-container-log`;
audit events -> `kube-system/kube-apiserver-<node>` (adapter `k8s-audit`, no instance);
`k8s.event.observed` about a pod -> its workload + pod instance (adapter `k8s-events`);
`k8s.resource.*` about workloads/pods -> workload service (adapter `k8s-inventory`).
API pods WITHOUT controller metadata from k8s_attributes are left unattributed in events
(absence of metadata is not evidence of a bare pod); the inventory still models them.

## B2-IC-7 K8S-002: ignore annotation-only writes (owner: C2) - PROPOSED

Observed live: `kubectl annotate` of the kubeadm bootstrap bindings (to mark them as accepted
risks) is a successful PATCH of a binding whose resulting object grants cluster-admin /
binds system:anonymous, so the audit side of K8S-002 matches it (confidence medium). The
normaliser now marks such writes (real fixture `tests/fixtures/kubernetes/audit/rbac_crb_annotate_patch.json`):
`attributes.metadata_only_change = true`, `attributes.metadata_fields_changed = ["annotations"]`.
Proposal for the audit CTE of `rules/kubernetes/K8S-002.sql`:

```sql
AND NOT (JSONExtractBool(attributes, 'metadata_only_change')
         AND JSONExtract(attributes, 'metadata_fields_changed', 'Array(String)') = ['annotations'])
```

Label changes stay in scope on purpose: labels drive ClusterRole aggregation
(`rbac.authorization.k8s.io/aggregate-to-*`), so a label-only patch can grant privileges.
`kind.sh` now patches the annotations only when they are missing, so this happens once per
cluster.
