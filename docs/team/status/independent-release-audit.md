# ExtorQ independent release audit

**Phase A verdict is NOT READY for release sign-off.** The current snapshot has demonstrated release blockers in evidence identity, detection completeness, and the regression suite. Fresh end-to-end evidence across all four asset classes is still unverified. This is the baseline and approval proposal. It sets the acceptance criteria for subsequent remediation and release phases.

## Storage inventory and clean-state plan

- **Declared ClickHouse database `extorq`.** Application tables include `events`; `assets`, `inventory_items`, `services`, `service_instances`; `scan_runs`, `finding_observations`; `detection_rules`, `rule_runs`, `alerts`, `alert_evidence`; `investigation_contexts`, `context_relationships`, `ai_assessments`; `analyst_state`, `analyst_actions`; `collector_health`, `pipeline_health`, `ingest_audit` and `ingest_quarantine`. `schema_migrations` is protected state. `simulation_runs` is legacy and migration 0008 drops the table plus four event/alert schema objects associated with simulation markers (one index and three columns). The deployed ledger and table counts remain unknown.
- **SQLite.** On-disk collector DBs and scanner outbox were queried in read-only mode for names and counts. Each observed outbox and dead-letter table had 0 rows at that read. Checkpoint/snapshot counts were macOS 1/1,370, Linux 3/1,432, Kubernetes inventory 1/304, GitHub repo 1/0, GitHub mechanics 2/0, SDK heartbeat 2/0, retired simulation 0/0, scanner outbox 0/0. Compose declares a shared gateway/writer `spool.db` with queued records, batch replay, deduplication, dead letters and counters, on an inaccessible Docker volume. OTel file offsets and queued requests are separate node-persistent state. The declared local validation report directory had no top-level report files at inspection. The tracked `eval/live` and `eval/jev` files are historical evidence, not current test outcomes.
- **Recoverability blocker.** The working reset script counts records, stops selected writers, truncates sequentially, clears the spool and collector state, and then restarts. It does not take or verify a restorable backup. The stop set omits the analyst API's mutation route, and the OTel queue can outlive a gateway stop. After a failure, the script can restart a partially reset stack. Source: `scripts/reset_data.py:52–60,370–394,476–512`. No dedicated disposable database or matching deployed code revision was established. Reset and migration 0008 were not executed.
- **Proposed isolation.** Pin the release input and off-line backup policy first. Use new named Compose storage and local bindings for the validation environment. Apply migrations to the empty store, verify the ledger and grants, and confirm that analyst data, historical test records and old queue contents are absent. Establish each source's baseline separately. Preserve source-native checkpoint and pending-exporter state when backing up the existing environment. Route validated producers explicitly and record fresh source-native test footprints after the cutover. A fresh receiver checkpoint may replay retained logs. Keeping a checkpoint and discarding its pending outbox can strand unsent records. Reconcile both cases explicitly before calling the store clean.
- **Any in-place reset.** Requires verified target identity and ownership, exact table and state scope, backups and a restore check, quiesced writers including analyst actions, scanner and external exporters, explicit permission and verified before/after counts. Backup handling must preserve local permissions and exclude credentials from reports and exports. Keep evidence needed for investigations and operational restore.

## Data-model assessment

The schema separates facts, inventory, findings, rule versions, evidence links and analyst workflow. Events use event and ingestion timestamps, monthly event-time partitions, a sorting key prefixed by asset and type, and a 90-day TTL. The source-aware contracts use UTC timestamps and nullable fields for unknowns. SQLite owns transactional ingestion state. ClickHouse's asynchronous merges make query-time deduplication necessary for dependent views and counts. Sorting by asset and type helps corresponding timeline queries. A rolling global event-ID lookup without time/asset pruning merits a measured query-plan review. [ClickHouse ReplacingMergeTree](https://clickhouse.com/blog/updates-in-clickhouse-1-purpose-built-engines)

Top priorities are a consistent evidence identity across SQLite and ClickHouse, aligned evidence retention, and truthful incomplete rule runs. Benchmark service drill-down, event ID lookups, multi-asset joins and finding summaries using `EXPLAIN indexes = 1`, read rows, memory and latency under representative volume. A canonical evidence key can reduce identity ambiguity while adding migration and view maintenance. Minimal retained evidence for long-lived alerts can bound retention cost. Query latency, cardinality and growth estimates need observed row counts and workload measurements.
