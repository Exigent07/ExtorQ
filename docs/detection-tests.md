# Detection tests: what fires, why, and how to trigger it

_Generated by `scripts/gen_detection_docs.py` from `rules/` and `detection_tests/`; the manual steps are the only hand-written part. Re-generate after changing a rule or a test._

Every test below is **real activity on a monitored asset**, not an inserted record: the telemetry travels the normal path and the rule that fires is the production rule. Run them all with `make test-detections` (after `make fast-on`), or one asset with `make test-detections-linux|kubernetes|github|macos`, CORR-002 with `make test-detections-corr`.

## 1. How a detection happens (applies to every test)

```
real activity ─► source (journald/auditd/audit log/GitHub API/unified log) ─► collector ─► gateway (TLS, token)
   ─► durable spool ─► writer ─► ClickHouse `events` ─► detector (runs each rule's SQL on a schedule)
   ─► `alerts` + `alert_evidence` ─► correlation builds an InvestigationContext ─► Jev advisory triage ─► console/API
```

* **Nothing is marked.** The tests perform the real action and are verified by asset + rule + time
  window; the telemetry carries no test marker. The detector treats it like any other activity.
* **Rules are deterministic SQL** over normalised events (`rules/<domain>/<ID>.sql`). Thresholds,
  windows and allowlists live in the rule's YAML `params`; the alert's `confidence` is computed
  from how complete the evidence is (for example two independent sources agreeing), never from AI.
* **Latency = source + collector + pipeline + detector.** With the default configuration an alert
  appears 1-5 minutes after the activity (collectors poll every 30-120 s, rules run every 60-120 s).
  The fast profile (`make fast-on`) polls every 10-15 s and runs rules every 10 s, so Linux,
  Kubernetes and macOS alerts appear in about 50-70 s and GitHub in 80-100 s (it polls an external
  API). A rule's window (for example 5 minutes for VM-001) is how far back it looks; it does not
  delay the alert.
* **Episodes.** Window-bucket rules merge activity into one alert while it keeps continuing (for
  example 15 minutes for K8S-003/K8S-004). A repeat inside that period extends the existing
  alert (`last_seen` moves) instead of creating a new one. This is intended: one burst, one alert.
* **Negative controls.** Every test also performs similar-looking benign activity that must NOT
  alert, and the runner proves the rule actually evaluated that activity (a rule run started after
  the control's telemetry was stored) before it accepts silence. A control that produces no
  telemetry cannot prove anything and is reported *inconclusive*, never a pass.
* **Shared NAT address.** Everything the Mac sends to the VM arrives from `10.0.2.2` (QEMU's NAT).
  Rules that group by source address therefore report confidence **medium/low**: the burst is real
  but its origin is not attributable. That is deliberate honesty, not a defect.

## 0. Setup for the manual steps

Run everything from the repository root with the stack up (`make up-full`), the VM up
(`make vm-up`), the cluster up (`make kind-up`) and the collectors running
(`make collectors-start`). For ~1-minute detection times switch on the fast profile first
(`make fast-on`, revert with `make fast-off`).

```bash
export ID=$(openssl rand -hex 3)          # artefacts are named extorq-test-$ID so they are easy to find and remove
vm() { ssh -i var/vm/keys/extorq-admin -p 2222 -o BatchMode=yes -o IdentitiesOnly=yes \
          -o UserKnownHostsFile=var/vm/known_hosts extorq-admin@127.0.0.1 "$@"; }
K="kubectl --kubeconfig var/kube/extorq-lab-admin.kubeconfig --context kind-extorq-lab"
api() { curl -s -H "Authorization: Bearer $(cat var/secrets/api_service_token)" \
          -H 'X-ExtorQ-User: me' -H 'X-ExtorQ-Role: viewer' "http://127.0.0.1:8000$1"; }
# newest alerts of a rule (id, asset, first/last seen, evidence count):
alerts() { api "/api/v1/alerts?rule_id=$1&limit=3" | python3 -c \
  "import sys,json; [print(a['alert_id'], a['asset_id'], a['first_seen'], a['event_count'], a['confidence']) for a in json.load(sys.stdin)['items']]"; }
# the evidence of one alert (must resolve to stored events; unresolved ids are listed separately):
evidence() { api "/api/v1/alerts/$1" | python3 -c \
  "import sys,json; d=json.load(sys.stdin); print(len(d['evidence']),'evidence events; unresolved:',d['unresolved_evidence_ids']); [print(' ',e['event_time'],e['event_type'],e['source_type']) for e in d['evidence'][:8]]"; }
```

Each test below says **how long to wait**. If you repeat a test right after a previous run, the
rule's earlier alert can still be open (see *Episodes* in section 1): new activity is then merged
into it instead of creating a new alert, so wait for the episode to close or look at the existing
alert's `last_seen`.

## 2. Ubuntu 24.04 VM lab-vm-01 (`linux:lab-vm-01`)

### VM-001: Burst of failed SSH authentication

* **Rule** `VM-001` v1.1.0, severity **medium**, ATT&CK T1110, T1110.001, T1110.003, runs every 60 s (look-back 900 s), dedup `window_bucket` (300 s buckets).
* **Telemetry it needs:** `linux.journald` → `auth.ssh.login_failed`, `auth.ssh.invalid_user`, `auth.ssh.preauth_closed`, `auth.ssh.max_auth_exceeded`.

**Why it fires.** Five or more distinct SSH connections (src_ip, src_port) from the same source address fail authentication against a Linux host within five minutes (sliding window), or one source accumulates ten or more 'Failed <method>' attempts in that window (several passwords per connection). Every sshd failure shape counts: failed password/key attempts, invalid users, clients that offered a rejected key and disconnected before authenticating, and 'maximum authentication attempts exceeded'. Evidence is the sshd log collected from journald. Confidence: high when the connection threshold is met from an attributable source; medium when the source is a shared NAT/gateway address or only the attempt threshold was met.

**Thresholds / parameters** (`params` in the rule YAML): `{"window_seconds":300,"threshold_connections":5,"threshold_failures":10,"shared_nat_ips":["10.0.2.2","127.0.0.1","::1"]}`

**What the automated test does** (`detection_tests`, test id `linux.vm-001`)

* Positive: From the Mac: 10 SSH connections to 127.0.0.1:2222 as root, admin, oracle, test and ubuntu, each offering a freshly generated throwaway key, plus one connection offering four keys (exceeds MaxAuthTries 3).
* Negative control (must NOT alert): Three successful key logins of the operator account extorq-admin.
* Cleanup: The throwaway keys are deleted; nothing is created on the VM.
* Expected: VM-001 on linux:lab-vm-01, src_ip 10.0.2.2, confidence medium (shared QEMU NAT address: the burst is real, its origin is not attributable).
* Why it is safe: Keys are random and authorised nowhere; password and keyboard-interactive authentication are disabled on both sides; any unexpected success stops the test.
* Evidence source and wait: journald on the VM (sshd, nginx, lab-portal), read every collector cycle

**Trigger it yourself** (wait: ~1 min with the fast profile)

```bash
KD=$(mktemp -d); for i in 0 1 2 3 4; do ssh-keygen -q -t ed25519 -N '' -C '' -f $KD/id_$i; done
S="ssh -p 2222 -o BatchMode=yes -o IdentitiesOnly=yes -o PreferredAuthentications=publickey \
   -o StrictHostKeyChecking=yes -o UserKnownHostsFile=var/vm/known_hosts -o ConnectTimeout=8"
for n in 1 2; do for u in root admin oracle test ubuntu; do $S -i $KD/id_0 $u@127.0.0.1 true 2>/dev/null; sleep 0.3; done; done
$S -i $KD/id_1 -i $KD/id_2 -i $KD/id_3 -i $KD/id_4 admin@127.0.0.1 true 2>/dev/null   # exceeds MaxAuthTries 3
rm -rf $KD                                       # cleanup: nothing exists on the VM
```
The keys are generated for this run and authorised nowhere, so every attempt fails.

**What you should see.** `alerts VM-001` shows `src_ip 10.0.2.2`, confidence **medium**; the evidence has the sshd `invalid_user` / `preauth_closed` / `max_auth_exceeded` events.

**False positives considered:**

* An administrator or automation repeatedly using a wrong key or password (for example a misconfigured Ansible inventory or CI deploy key) from one host. Handling: the threshold (five failed connections in five minutes from one address) is above what a person retrying a typo produces; successful logins are never counted, so a client that eventually authenticates with the right key adds nothing.
* Several legitimate users behind one NAT or VPN egress address mistyping credentials at the same time. Handling: shared NAT/gateway addresses are configured (shared_nat_ips) and lower confidence to medium. On the monitored VM every connection from the Mac host arrives from the QEMU gateway 10.0.2.2, so such alerts are always medium.
* Vulnerability scanners or SSH health checks that open many unauthenticated connections. Handling: no source allowlist (addresses are not identities); the alert shows the usernames tried and the connection count so a scheduled scan is recognisable.

**Blind spots (what this rule cannot see):**

* Low-and-slow guessing below five failed connections (or ten failed attempts) per five minutes per source address.
* Distributed guessing from many source addresses (one or two attempts each).
* Successful logins are not evaluated here; success after failures is shown by the investigation context (ssh_success_after_failures), not by this rule.
* Authentication handled outside sshd/journald (a PAM module logging elsewhere), and lines journald dropped under rate limiting.
* Attempts that never reach sshd authentication (connections refused by a firewall).

### VM-002: systemd unit created and enabled (persistence)

* **Rule** `VM-002` v1.4.0, severity **high**, ATT&CK T1543.002, runs every 60 s (look-back 1800 s), dedup `event`.
* **Telemetry it needs:** `linux.inventory` → `persistence.systemd.unit_created`, `persistence.systemd.unit_modified`, `persistence.systemd.unit_enabled`; `linux.auditd` → `file.audit.watch`.

**Why it fires.** A systemd unit file appeared or changed in a persistence location on a Linux host (or an existing unit was newly enabled), as observed by comparing inventory snapshots collected over SSH. Confidence: high when an auditd file watch hit (key extorq_systemd) creates or modifies the same path no more than two minutes before the inventory observation; medium for the inventory diff alone and for enable-only changes. Deletions and other auditd hits corroborate nothing. Unit state changes (start, stop, restart) are not persistence and are never evaluated. Exact allowlisted paths and the collector's baseline snapshot are not alerted.

**Thresholds / parameters** (`params` in the rule YAML): `{"audit_key":"extorq_systemd","corroboration_seconds":120,"allowlist_paths":[],"allowlist_units":[]}`

**What the automated test does** (`detection_tests`, test id `linux.vm-002`)

* Positive: As extorq-admin with sudo: write /etc/systemd/system/extorq-test-<id>.service (Type=oneshot, ExecStart=/bin/true), daemon-reload, enable. The unit is never started.
* Negative control (must NOT alert): Restart the existing cron.service (a state change, no unit file changes).
* Cleanup: Disable and delete the unit, daemon-reload, verify the file and symlink are gone.
* Expected: VM-002 on linux:lab-vm-01 for the new unit, confidence high when the auditd write and the inventory diff agree on the path.
* Why it is safe: The unit only runs /bin/true and is never started; it exists for minutes.
* Evidence source and wait: VM inventory diff (systemd units, local accounts, cron) plus auditd

**Trigger it yourself** (wait: ~1 min)

```bash
vm "sudo tee /etc/systemd/system/extorq-test-$ID.service >/dev/null" <<'UNIT'
[Unit]
Description=Nightly cache warm-up

[Service]
Type=oneshot
ExecStart=/bin/true

[Install]
WantedBy=multi-user.target
UNIT
vm "sudo systemctl daemon-reload && sudo systemctl enable extorq-test-$ID.service"   # never started
# negative control: a state change without a unit file change
vm "sudo systemctl restart cron.service"
# cleanup
vm "sudo systemctl disable extorq-test-$ID.service; sudo rm -f /etc/systemd/system/extorq-test-$ID.service; sudo systemctl daemon-reload"
```

**What you should see.** Alert for `/etc/systemd/system/extorq-test-$ID.service`. Confidence **high** when the auditd write and the inventory diff agree on the path (two independent sources).

**False positives considered:**

* Package installation or upgrade that ships or updates a unit. Handling: vendor units under /usr/lib/systemd are flagged (vendor_unit) and the investigation context shows the package.* changes of the asset; no package-name allowlist (an attacker can name a unit after a package).
* Configuration management or an administrator deploying a service. Handling: exact unit paths controlled by that process can be allowlisted (allowlist_paths); a path is used instead of a unit name because only root can write those directories, and config.file.changed keeps monitoring the allowlisted file.
* Re-installing an unchanged unit file (a redeploy) is a genuine write that auditd records. Handling: rewriting identical content produces no inventory diff, so nothing alerts; a delete and re-create with identical content extends the existing alert, because the alert identity includes the content digest.

**Blind spots (what this rule cannot see):**

* Units created and removed between two inventory snapshots (short-lived persistence); auditd still records the write but this rule triggers on the inventory diff only.
* Persistence through other mechanisms (cron, shell profiles, rc.local, timers outside watched directories, user units outside the collected paths).
* Allowlisting is path-based: an attacker able to write an allowlisted unit evades this rule (config.file.changed monitoring of that path is the compensating control).
* Without auditd (missing_sources), the writer process is unknown and confidence is medium.
* Audit logs written without ENRICHED syscall names (numeric syscall values only) never corroborate (allowlist of names; fail closed): the alert still fires from the inventory diff, with confidence medium.

### VM-003: Local account created

* **Rule** `VM-003` v1.0.0, severity **medium**, ATT&CK T1136.001, runs every 60 s (look-back 1800 s), dedup `event`.
* **Telemetry it needs:** `linux.inventory` → `account.user.created`; `linux.auditd` → `file.audit.watch`.

**Why it fires.** A local user account appeared on a Linux host between two inventory snapshots of /etc/passwd (account.user.created). New local accounts are a common persistence and backdoor technique; on a managed server they are rare and should be explainable. Confidence: high when an auditd identity-file watch hit (key extorq_identity: a successful create or modify syscall on /etc/passwd or /etc/shadow, such as useradd's openat and rename) precedes the snapshot that first saw the account, so two independent sources agree and the writing executable is known; medium for the inventory diff alone. The alert reports the uid, shell, home, groups, whether the uid is 0 (a second root), whether the uid is in the system range and whether the account has a login shell or privileged group membership.

**Thresholds / parameters** (`params` in the rule YAML): `{"audit_key":"extorq_identity","identity_files":["/etc/passwd","/etc/shadow"],"corroboration_seconds":600,"uid_min":1000,"nologin_shells":["/usr/sbin/nologin","/sbin/nologin","/bin/false","/usr/bin/false"]}`

**What the automated test does** (`detection_tests`, test id `linux.vm-003`)

* Positive: As extorq-admin with sudo: useradd --no-create-home --shell /usr/sbin/nologin extorq-test-<id>.
* Negative control (must NOT alert): Remove the account again (the cleanup of the positive phase): VM-003 fires on a NEW account, never on removal, and the inventory diff must report the removal.
* Cleanup: userdel (and groupdel of a leftover private group); verify it is gone.
* Expected: VM-003 on linux:lab-vm-01 for the new account (inventory diff).
* Why it is safe: The account has no password, no home directory and a non-login shell.
* Evidence source and wait: VM inventory diff (systemd units, local accounts, cron) plus auditd

**Trigger it yourself** (wait: ~1 min)

```bash
vm "sudo useradd --no-create-home --shell /usr/sbin/nologin --comment 'Build agent' extorq-test-$ID"
# cleanup (the removal is also the negative control: removal must NOT alert)
vm "sudo userdel extorq-test-$ID; sudo groupdel extorq-test-$ID 2>/dev/null; getent passwd extorq-test-$ID || echo removed"
```

**What you should see.** Alert naming the new account (inventory diff of /etc/passwd, corroborated by auditd identity-file writes).

**False positives considered:**

* Package installation that creates a service account (adduser --system: system-range uid, no login shell, often no home). Handling: reported, not suppressed. The alert shows system_uid_range and login_shell, and the investigation context lists the asset's package.* changes; an account created alongside a package install is closed as benign after checking the package. No uid-range or shell allowlist because an attacker can choose both (the matrix test itself uses a nologin account).
* Provisioning or configuration management creating users for people. Handling: expected accounts are recognisable by the writer executable (useradd/adduser run by the automation's user, from the auditd corroboration) and the change ticket; there is no account-name allowlist because names are chosen by whoever creates the account.

**Blind spots (what this rule cannot see):**

* Accounts created and deleted between two inventory snapshots (60 s): the auditd write of /etc/passwd is still recorded and visible in the investigation context, but no account.user.created event exists, so this rule does not fire.
* Changes to existing accounts (uid changed to 0, a login shell added, a user added to the sudo group) are not account creations; privileged group changes appear as config.file.changed on /etc/group.
* Accounts from directory services (LDAP/SSSD, NSS modules) never appear in /etc/passwd.
* Without auditd (missing_sources) the writer is unknown and confidence stays medium; audit logs without enriched syscall names never corroborate (fail closed).

### VM-004: Cron persistence file added

* **Rule** `VM-004` v1.0.0, severity **high**, ATT&CK T1053.003, runs every 60 s (look-back 1800 s), dedup `event`.
* **Telemetry it needs:** `linux.inventory` → `persistence.cron.changed`; `linux.auditd` → `file.audit.watch`.

**Why it fires.** A cron file was added or modified on a Linux host (system crontab, /etc/cron.d, the hourly/daily/weekly/monthly script directories or a user crontab), as observed by comparing inventory snapshots collected over SSH. cron runs these entries without any further user action, so a new entry is persistence even before it first runs. Removals are not alerted. Confidence: high when an auditd watch hit (key extorq_cron) records a successful create or modify syscall on exactly that file shortly before the snapshot (two sources agree; the writing executable is known); medium for the inventory diff alone, which is always the case for locations without an audit watch.

**Thresholds / parameters** (`params` in the rule YAML): `{"audit_key":"extorq_cron","corroboration_seconds":600,"snapshot_read_lag_seconds":5,"allowlist_paths":[],"package_manager_executables":["/usr/bin/dpkg","/usr/bin/apt","/usr/bin/apt-get"]}`

**What the automated test does** (`detection_tests`, test id `linux.vm-004`)

* Positive: As extorq-admin with sudo: write /etc/cron.d/extorq-test-<id> with one job that runs /bin/true once a year (03:17 on 1 January).
* Negative control (must NOT alert): Remove the cron file again (the cleanup of the positive phase): VM-004 fires on an added or changed cron file, and the inventory diff must report the removal.
* Cleanup: Delete the cron file and verify it is gone.
* Expected: VM-004 on linux:lab-vm-01 for the added cron file (inventory diff).
* Why it is safe: The job only runs /bin/true and is scheduled far outside the test window.
* Evidence source and wait: VM inventory diff (systemd units, local accounts, cron) plus auditd

**Trigger it yourself** (wait: ~1 min)

```bash
vm "sudo tee /etc/cron.d/extorq-test-$ID >/dev/null" <<'CRON'
# Rotate application cache
SHELL=/bin/sh
PATH=/usr/sbin:/usr/bin:/sbin:/bin
17 3 1 1 * root /bin/true
CRON
vm "sudo rm -f /etc/cron.d/extorq-test-$ID"    # cleanup (the removal is the negative control)
```
The job runs `/bin/true` once a year, so nothing runs during the test.

**What you should see.** Alert for the added `/etc/cron.d` file (inventory diff + auditd write).

**False positives considered:**

* Package installs and upgrades that ship or update cron files (sysstat, logrotate, e2scrub). Handling: reported with the writer (package_manager_writer = true when dpkg wrote /etc/cron.d) and the asset's package.* changes in the investigation context; not suppressed, because root can also install a malicious package with dpkg.
* Administrators or configuration management deploying scheduled jobs. Handling: exact paths of files that a controlled process owns can be allowlisted (allowlist_paths); paths rather than file names because only root can write these directories.

**Blind spots (what this rule cannot see):**

* The inventory records a content digest, not the cron entry itself (file contents are never collected), so the alert says that a file changed, not which command it schedules.
* Entries added and removed between two inventory snapshots (60 s); systemd timers (covered by VM-002 when the unit is new), at jobs, shell profiles and other persistence.
* User crontabs in /var/spool/cron/crontabs are only seen when the collector can read that directory; only /etc/cron.d has an auditd watch, so other locations are medium.
* Removing a cron file is not alerted (deletion is not persistence).

### CORR-002: Ordered probing, SSH failures and systemd persistence on one host

* **Rule** `CORR-002` v1.3.0, severity **high**, ATT&CK T1595.003, T1110, T1543.002, runs every 120 s (look-back 2700 s), dedup `window_bucket` (1800 s buckets).
* **Telemetry it needs:** `linux.nginx` → `http.request`; `linux.apache` → `http.request`; `linux.app` → `http.request`; `linux.journald` → `auth.ssh.login_failed`, `auth.ssh.invalid_user`, `auth.ssh.preauth_closed`, `auth.ssh.max_auth_exceeded`; `linux.inventory` → `persistence.systemd.unit_created`, `persistence.systemd.unit_modified`, `persistence.systemd.unit_enabled`; `linux.auditd` → `file.audit.watch`.

**Why it fires.** Multi-stage sequence on one Linux host, in this order within 30 minutes: (1) HTTP probing (at least 10 client-error responses to one source, including at least 5 distinct probe-like routes, within 5 minutes), (2) SSH authentication failures (at least 3 failed connections or 5 failed attempts from one source within 5 minutes), (3) an unexpected systemd persistence change with creation or modification evidence (unit created, modified or enabled outside the allowlist, or a successful auditd create/modify syscall on a unit file; deletions are context only). The rule shows ordered co-occurrence of independent observations across three services (web server, sshd, systemd); it does not establish that one stage caused the next or that one actor performed all of them. Confidence: medium when the probing and the SSH failures share a source address that is not a shared NAT/gateway address; low otherwise.

**Thresholds / parameters** (`params` in the rule YAML): `{"sequence_seconds":1800,"probe_window_seconds":300,"probe_min_requests":10,"probe_min_routes":5,"probe_route_pattern":"(?i)(\\.env|\\.git|\\.svn|\\.aws|\\.ssh|\\.ht(access|passwd)|wp-|wordpress|phpmyadmin|xmlrpc|cgi-bin|server-status|actuator|/admin|/manager|/console|/shell|/backup|/config|/debug|/vendor/|/etc/passwd|\\.\\./|\\.php|\\.asp|\\.jsp|/solr|/jenkins|/boaform|/hnap1|/owa|/remote/|/druid|/telescope)","ssh_window_seconds":300,"ssh_min_connections":3,"ssh_min_failures":5,"audit_key":"ext`

**What the automated test does** (`detection_tests`, test id `linux.corr-002`)

* Positive: Within a few minutes, in this order: the HTTP-001 probe requests, the VM-001 SSH burst, and the VM-002 unit creation (extorq-test-<id>.service).
* Negative control (must NOT alert): Run FIRST: the VM-001 SSH burst alone (no probing in the preceding 30 minutes, no persistence after it).
* Cleanup: Disable and delete the unit; delete the throwaway SSH keys.
* Expected: CORR-002 on linux:lab-vm-01, confidence low (all stages come from the shared NAT address 10.0.2.2: ordered co-occurrence, never causation). HTTP-001, VM-001 and VM-002 alert as well.
* Why it is safe: The union of the HTTP-001, VM-001 and VM-002 safety properties.
* Evidence source and wait: VM inventory diff (systemd units, local accounts, cron) plus auditd

**Trigger it yourself** (wait: ~2-3 min, and it needs **30 quiet minutes** (no HTTP probing/SSH bursts) before it starts)

Run the three stages **in this order within a few minutes**, as one story:

1. HTTP probing (the HTTP-001 commands above)
2. an SSH failure burst (the VM-001 commands above)
3. a systemd persistence change (the VM-002 commands above, but leave the unit in place until the alert appears)

Negative control (run it first, alone): only the SSH burst, with no probing in the previous 30 minutes.

**What you should see.** CORR-002 at **low** confidence (all stages share the NAT address, so it is ordered co-occurrence, never causation); HTTP-001, VM-001 and VM-002 alert as well.

**False positives considered:**

* Unrelated activity that happens to line up: an internet scanner probing the web server, a different client mistyping an SSH password and an administrator installing a service within the same half hour. Handling: the stages must occur in order within 30 minutes and each must reach its own threshold; confidence stays low unless the probing and the SSH failures share a source IP that is not a shared NAT address, and even then a shared IP is not proof of one actor (causation_established is always false).
* Penetration tests and vulnerability scans that cover web and SSH, followed by planned maintenance. Handling: no suppression; the alert names the units and their writers so the persistence change can be checked against change records.
* Every connection from the Mac host reaches the VM from the QEMU gateway 10.0.2.2, so a shared source IP there carries no identity. Handling: shared NAT/gateway addresses are configured (shared_nat_ips) and keep the confidence low.
* Re-installing an unchanged unit file is a genuine write and counts (observed live: the VM redeploy runs install on lab-portal.service: unlinkat, openat CREATE, fchownat, fchmodat). Handling: the features separate persistence_units_inventory_confirmed (the inventory saw new or changed content) from persistence_units_audit_only (write seen by auditd only), and persistence_writers names the writing executable.

**Blind spots (what this rule cannot see):**

* Sequences slower than 30 minutes, probing below the thresholds, or SSH failures below the thresholds (each stage alone is covered by HTTP/VM-001 style rules).
* Persistence other than systemd units (cron, shell profiles, SSH keys) and changes the inventory diff misses between snapshots without an auditd watch hit.
* Web servers whose access logs are not collected (only nginx, Apache and the web app are parsed), probing over TLS-terminating proxies that hide the client address, and SSH on hosts without journald collection.
* A stage that happened before the evaluation lookback (45 minutes) is not considered.
* auditd logs without ENRICHED syscall names (numeric syscall values) never count as stage 3 (fail closed); the inventory diff still does.

### HTTP-001: Web probing from one source

* **Rule** `HTTP-001` v1.1.0, severity **low**, ATT&CK T1595.003, runs every 60 s (look-back 900 s), dedup `window_bucket` (300 s buckets).
* **Telemetry it needs:** `linux.nginx` → `http.request`; `linux.apache` → `http.request`; `linux.app` → `http.request`; `k8s.container_log` → `http.request`.

**Why it fires.** One source receives at least 10 client-error (4xx) responses from one asset within five minutes (sliding window), and at least 5 of the requested routes are distinct probe-like paths (.env, .git, wp-login.php, phpmyadmin, server-status, admin consoles, ...). Evidence is the web server or application access log (nginx/Apache/the web application on Linux hosts, the web application's container log in Kubernetes). Both conditions are required: ordinary 404s (missing assets) never count as probe routes and successful requests never count at all. Confidence: high when the source is attributable; medium when it is a shared NAT/gateway address (the probing is real, its origin is not attributable).

**Thresholds / parameters** (`params` in the rule YAML): `{"window_seconds":300,"min_requests":10,"min_probe_routes":5,"probe_route_pattern":"(?i)(\\.env|\\.git|\\.svn|\\.aws|\\.ssh|\\.ht(access|passwd)|wp-|wordpress|phpmyadmin|xmlrpc|cgi-bin|server-status|actuator|/admin|/manager|/console|/shell|/backup|/config|/debug|/vendor/|/etc/passwd|\\.\\./|\\.php|\\.asp|\\.jsp|/solr|/jenkins|/boaform|/hnap1|/owa|/remote/|/druid|/telescope)","shared_nat_ips":["10.0.2.2","172.18.0.1","10.244.0.1","127.0.0.1","::1"]}`

**What the automated test does** (`detection_tests`, test id `linux.http-001`)

* Positive: From the Mac: GET 14 paths web scanners request (/.env, /.git/config, /wp-login.php, /phpmyadmin/, /server-status, /admin, ...) on 127.0.0.1:8088; at least 12 must be answered with 4xx.
* Negative control (must NOT alert): 20 ordinary requests (/ and /healthz) answered 200.
* Cleanup: Nothing to remove (requests only).
* Expected: HTTP-001 on linux:lab-vm-01, src_ip 10.0.2.2, confidence medium.
* Why it is safe: Read-only GET requests to the lab portal; nothing on the VM changes.
* Evidence source and wait: journald on the VM (sshd, nginx, lab-portal), read every collector cycle

**Trigger it yourself** (wait: ~1 min)

```bash
for p in /.env /.git/config /wp-login.php /phpmyadmin/ /server-status /admin /actuator/health \
         /.aws/credentials /config.php /backup.zip /cgi-bin/test.cgi /xmlrpc.php /.svn/entries /jenkins/login; do
  curl -s -o /dev/null -w "%{http_code} $p\n" http://127.0.0.1:8088$p
done                                              # at least 12 must be 4xx
# negative control: ordinary traffic
for i in $(seq 10); do curl -s -o /dev/null http://127.0.0.1:8088/; curl -s -o /dev/null http://127.0.0.1:8088/healthz; done
```

**What you should see.** Alert from `10.0.2.2` with the probe routes listed; evidence is the nginx `http.request` events (journald).

**False positives considered:**

* Authorised vulnerability scanners and uptime checkers that request well-known paths. Handling: no source-address allowlist (addresses are not identities); the alert lists the probe routes, statuses and user agents so a scheduled scan is recognisable, and the severity is low because probing alone changes nothing on the host.
* Broken links or a misconfigured client repeatedly requesting missing admin or config paths. Handling: both thresholds must hold (10 client errors AND 5 distinct probe-like routes in 5 minutes); ordinary 404s for assets and pages never match the probe pattern.
* Behind a shared NAT or proxy address (10.0.2.2 for the VM, 10.244.0.1 for traffic that reaches the cluster web application through the NodePort) many clients share one source IP. Handling: confidence medium for configured shared addresses.

**Blind spots (what this rule cannot see):**

* Slow or distributed probing below 10 client errors / 5 probe routes per 5 minutes per source address.
* Probes that receive 2xx/3xx answers (an existing path) or 5xx errors are not counted.
* Probe paths outside the pattern, query-string payloads (routes never include the query string) and request bodies are not inspected.
* Web servers whose access logs are not collected.

### APP-001: Burst of failed web application logins

* **Rule** `APP-001` v1.1.0, severity **medium**, ATT&CK T1110.001, T1110.003, runs every 60 s (look-back 900 s), dedup `window_bucket` (300 s buckets).
* **Telemetry it needs:** `linux.app` → `app.auth.login_failed`; `k8s.container_log` → `app.auth.login_failed`.

**Why it fires.** An instrumented web application reports repeated failed logins: at least 5 for one user name within five minutes (password guessing against one account), or at least 5 from one source address across at least 3 user names (password spraying). Evidence is the application's own structured authentication events (the web application on the Linux VM, and the same application deployed in Kubernetes), never inferred from HTTP status codes. Confidence: high when every source address is known and none is a shared NAT/gateway address; medium otherwise (the attempts are real, their origin is not attributable).

**Thresholds / parameters** (`params` in the rule YAML): `{"window_seconds":300,"min_failures":5,"min_spray_users":3,"shared_nat_ips":["10.0.2.2","172.18.0.1","10.244.0.1","127.0.0.1","::1"]}`

**What the automated test does** (`detection_tests`, test id `linux.app-001`)

* Positive: From the Mac: 6 failed POST /login for the demo account lab-admin with random wrong passwords (127.0.0.1:8088, JSON).
* Negative control (must NOT alert): 1 failed login from the Mac, then 1 successful login performed inside the VM (the demo credential never leaves the VM).
* Cleanup: Nothing to remove (one portal session expires on its own).
* Expected: APP-001 on linux:lab-vm-01, variant guessing, user lab-admin.
* Why it is safe: Wrong passwords are random; the real credential is read by root on the VM and only the HTTP status is printed.
* Evidence source and wait: journald on the VM (sshd, nginx, lab-portal), read every collector cycle

**Trigger it yourself** (wait: ~1 min)

```bash
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8088/login \
       -H 'Content-Type: application/json' -d "{\"username\":\"lab-admin\",\"password\":\"wrong-$RANDOM\"}"
done                                              # each answers 401
```
The negative control (one successful login) is performed *inside* the VM so the demo credential never leaves it.

**What you should see.** Alert variant *guessing* for user `lab-admin` (6 `app.auth.login_failed` events from the portal's JSON log).

**False positives considered:**

* A user who forgot a password and retries, or a client with stale saved credentials. Handling: five failures for one user in five minutes is above ordinary retrying; a single failure followed by a success never alerts.
* Automated tests or monitoring that log in with a wrong or rotated credential. Handling: no user or address allowlist (both are attacker-supplied); the alert lists the user names, sources and failure reasons so the automation is recognisable.
* Behind a shared NAT/proxy address many users share one source (spraying variant). Handling: confidence medium for configured shared addresses. Every request from the Mac reaches the VM application from 10.0.2.2 and the cluster application from 10.244.0.1.

**Blind spots (what this rule cannot see):**

* Applications that do not emit structured authentication events.
* Slow guessing below 5 attempts per 5 minutes per user, and spraying with fewer than 3 user names per source.
* User names are attacker-supplied text; guessing with many distinct names from many sources is only visible as HTTP-level activity (HTTP-001 for probe paths).

## 3. kind cluster extorq-lab (`k8s:extorq-lab`)

### K8S-001: Privileged pod denied by Pod Security admission

* **Rule** `K8S-001` v1.1.0, severity **medium**, ATT&CK T1610, T1611, runs every 60 s (look-back 900 s), dedup `event`.
* **Telemetry it needs:** `k8s.audit` → `k8s.api.request`.

**Why it fires.** A request to create a pod (or add an ephemeral container) asking for privileged mode, host namespaces (hostNetwork/hostPID/hostIPC), hostPath volumes or dangerous added capabilities was rejected with HTTP 403 because it violates the namespace's Pod Security Standard. The control worked; the alert records who tried to run a privileged workload, where, and with which settings. Evidence is the kube-apiserver audit event (ResponseComplete stage) normalised by the OTLP audit pipeline. Confidence: high when the request body's risk flags and the Pod Security violation text both name a privileged control; medium when only one of them does (for example the body was not logged). Admitted privileged pods are K8S-005.

**Thresholds / parameters** (`params` in the rule YAML): `{"privileged_flags":["privileged","host_pid","host_network","host_ipc","host_path","host_path_root","dangerous_capabilities"],"violation_pattern":"privileged \\(|host namespaces|hostPath volumes|hostPort|non-default capabilities|unrestricted capabilities"}`

**What the automated test does** (`detection_tests`, test id `kubernetes.k8s-001`)

* Positive: kubectl create of a privileged, hostPID pod extorq-test-<id> in extorq-restricted (Pod Security baseline enforced): the API server answers 403.
* Negative control (must NOT alert): A restricted-compliant pod in extorq-restricted: admitted (201), then deleted.
* Cleanup: Delete the pods (the denied one never exists) and verify they are gone.
* Expected: K8S-001 on k8s:extorq-lab for the denied request (one alert per audit id).
* Why it is safe: The privileged pod is denied; the compliant pod is never scheduled.
* Evidence source and wait: kube-apiserver audit log via the OTel DaemonSet (k8s.audit)

**Trigger it yourself** (wait: ~1 min)

```bash
cat <<EOF | $K create -f -          # EXPECTED: Error ... forbidden: violates PodSecurity "baseline:latest"
apiVersion: v1
kind: Pod
metadata: {name: extorq-test-$ID, namespace: extorq-restricted}
spec:
  hostPID: true
  automountServiceAccountToken: false
  restartPolicy: Never
  nodeSelector: {kubernetes.io/hostname: extorq-test-unscheduled}   # can never be scheduled
  containers:
  - {name: worker, image: "alpine:3.19", command: ["sleep","300"], securityContext: {privileged: true}}
EOF
```
The API server refuses it (HTTP 403), so no pod exists and nothing needs cleanup. Negative control: the same pod without `privileged`/`hostPID` and with a restricted securityContext is admitted (201); delete it afterwards.

**What you should see.** Alert from the kube-apiserver **audit log** (shipped by the OTel DaemonSet): verb `create`, resource `pods`, response code **403**, the PodSecurity violation text. One alert per audit id.

**False positives considered:**

* An administrator deploying a legitimate node agent (CNI, CSI driver, log collector) into a namespace whose Pod Security level does not allow it. Handling: not suppressed; the fix is a dedicated privileged namespace for the agent, after which its pods are admitted and evaluated by K8S-005 instead.
* Server-side dry runs (kubectl --dry-run=server) are denied the same way. Handling: alerted (reconnaissance of the admission policy) with features.dry_run = true.
* Controllers retrying a privileged Deployment/DaemonSet in a restricted namespace produce one denial per retry and therefore one alert per audit id. Handling: the alerts share the group cluster|namespace|user, so the console shows them as one recurring source.

**Blind spots (what this rule cannot see):**

* Privileged pods admitted in namespaces with a permissive Pod Security level (or by exempt users) are not denied and therefore not detected here (K8S-005 covers admissions).
* Requests whose audit body was not logged (audit level Metadata) carry no risk flags; the rule then relies on the violation text (confidence medium).
* Violations of other Pod Security controls (runAsNonRoot, seccomp, ...) alone are not in scope.
* Audit pipeline outages (OTel collector, gateway) hide denials; see collector health.

### K8S-002: Risky RBAC grant (cluster-admin)

* **Rule** `K8S-002` v1.3.0, severity **high**, ATT&CK T1098, T1078.004, runs every 60 s (look-back 1800 s), dedup `event`.
* **Telemetry it needs:** `k8s.audit` → `k8s.api.request`; `k8s.api_inventory` → `k8s.resource.created`, `k8s.resource.updated`.

**Why it fires.** A Role, ClusterRole, RoleBinding or ClusterRoleBinding was created or changed so that it grants risky privileges: cluster-admin, wildcard verbs/resources, escalate/bind/impersonate, secrets read, pods/exec, or binds broad subjects (system:anonymous, system:unauthenticated, system:authenticated, all service accounts, default service accounts). Evidence comes from the kube-apiserver audit log (successful write, actor known) and/or the API inventory diff (resulting object state); both use the same risk vocabulary. Confidence is high when audit and inventory agree on object UID, resource version and risk signature. Other matches remain medium. Annotation-only writes and the documented kubeadm bootstrap objects created at cluster birth by the bootstrap identity are not alerted (narrow, documented baseline exception).

**Thresholds / parameters** (`params` in the rule YAML): `{"excluded_users":["system:serviceaccount:kube-system:clusterrole-aggregation-controller","system:apiserver"],"ignorable_metadata_fields":["annotations"],"bootstrap_users":["kubernetes-super-admin","kubernetes-admin"],"bootstrap_window_seconds":600,"bootstrap_lead_seconds":60,"bootstrap_objects":["clusterrolebindings||kubeadm:cluster-admins|ClusterRole/cluster-admin|Group:kubeadm:cluster-admins","rolebindings|kube-public|kubeadm:bootstrap-signer-clusterinfo|Role/kubeadm:bootstrap-signer-clusteri`

**What the automated test does** (`detection_tests`, test id `kubernetes.k8s-002`)

* Positive: Create ServiceAccount extorq-apps/extorq-test-<id> and a ClusterRoleBinding extorq-test-<id> granting it cluster-admin.
* Negative control (must NOT alert): Create another ServiceAccount and a RoleBinding in extorq-apps to the built-in read-only ClusterRole view.
* Cleanup: Delete the bindings and the service accounts; verify they are gone.
* Expected: K8S-002 on k8s:extorq-lab for the ClusterRoleBinding, confidence high when the audit write and the inventory diff agree.
* Why it is safe: The service accounts have no token (automount disabled, no token Secret): nobody can authenticate as them; the binding exists only until the alert is observed.
* Evidence source and wait: Kubernetes API inventory diff (k8s.api_inventory) and the audit log

**Trigger it yourself** (wait: ~1 min)

```bash
$K -n extorq-apps create serviceaccount extorq-test-$ID
$K create clusterrolebinding extorq-test-$ID --clusterrole=cluster-admin --serviceaccount=extorq-apps:extorq-test-$ID
# negative control: a read-only grant is not risky
$K -n extorq-apps create serviceaccount extorq-test-ro-$ID
$K -n extorq-apps create rolebinding extorq-test-ro-$ID --clusterrole=view --serviceaccount=extorq-apps:extorq-test-ro-$ID
# cleanup
$K delete clusterrolebinding extorq-test-$ID; $K -n extorq-apps delete rolebinding,serviceaccount extorq-test-ro-$ID; $K -n extorq-apps delete serviceaccount extorq-test-$ID
```

**What you should see.** Alert for the ClusterRoleBinding, flag `cluster_admin`. Confidence **high** when the audit write and the inventory diff agree on the **same object UID and resource version**.

**False positives considered:**

* Installing operators or Helm charts that legitimately ship cluster-admin bindings or wildcard ClusterRoles. Handling: reported with the actor and the object; no name or namespace allowlist (object names are chosen by whoever writes them).
* Administrators granting temporary elevated access during an incident or upgrade. Handling: reported; the risk signature (sorted risky flags) is part of the identity, so one grant is one alert.
* Re-applying an unchanged risky object produces an update event with the same risk signature. Handling: it extends the existing alert instead of creating a new one.
* Observed live (2026-11-21): kubeadm's own bootstrap bindings (kubeadm:cluster-admins, kube-public/kubeadm:bootstrap-signer-clusterinfo) alerted at cluster creation, and a kubectl annotate marking them as accepted risks alerted again as patches. Handling (v1.1.0): exactly these two creates at cluster birth by the bootstrap identity are excepted (identity AND exact object signature AND time anchor), and annotation-only writes are ignored; any other write to them still alerts.
* Bindings of a service account to built-in read-only roles (view). Handling: not risky by the shared risk vocabulary (no flag in risky_flags), so they never alert; the matrix negative control checks exactly this.

**Blind spots (what this rule cannot see):**

* Privileges obtained without touching RBAC objects (e.g. stolen tokens of an existing privileged service account, node credentials) are out of scope.
* Changes by the excluded system controllers, and inventory-only observations of objects named 'system:*' (bootstrap defaults), are ignored; the audit side still sees writes to 'system:*' objects by any other actor.
* Aggregated ClusterRoles gain rules through the aggregation controller (excluded); the triggering label change on the source role is visible only if that role is itself risky.
* Without the audit source (missing_sources) the actor is unknown and only the state diff is evaluated (confidence medium).
* Bootstrap exception: an actor holding kubeadm's bootstrap credentials during the first 10 minutes after the cluster's birth who creates exactly the two documented kubeadm objects (same names, roleRefs and subjects) is not alerted; those objects grant nothing beyond what kubeadm grants by design, and the posture scan still reports them.
* Annotation-only writes are trusted on B2's normaliser classification of the request body (metadata_only_change); a write without that attribute is evaluated normally.

### K8S-003: Interactive exec into a pod

* **Rule** `K8S-003` v1.0.0, severity **medium**, ATT&CK T1609, runs every 60 s (look-back 1800 s), dedup `window_bucket` (900 s buckets).
* **Telemetry it needs:** `k8s.audit` → `k8s.api.request`.

**Why it fires.** A person opened an exec or attach session into a running pod (kubectl exec / attach), as recorded by the kube-apiserver audit log. Exec gives command execution inside the container with its service account token, mounted secrets and network position, so on a production cluster it should be rare and explainable. Only sessions the API server accepted count (101 Switching Protocols or 2xx; kubectl's WebSocket GET and the legacy SPDY POST). Control-plane components and all service accounts (every 'system:' identity) are excluded by design; reviewed automation with a non-system identity can be excluded by exact identity. Repeated sessions by one person into one pod within 15 minutes are one alert. Confidence: high when the target pod is named and the session was established; medium otherwise.

**Thresholds / parameters** (`params` in the rule YAML): `{"subresources":["exec","attach"],"excluded_users":[]}`

**What the automated test does** (`detection_tests`, test id `kubernetes.k8s-003`)

* Positive: kubectl exec into the running lab-portal pod, running `id`.
* Negative control (must NOT alert): kubectl logs --tail=5 of the same pod.
* Cleanup: Nothing to remove (`id` only reads; the exec session ends with the command).
* Expected: K8S-003 on k8s:extorq-lab naming the pod, container and user.
* Why it is safe: `id` changes nothing; its output is discarded; the pod is not modified.
* Evidence source and wait: kube-apiserver audit log via the OTel DaemonSet (k8s.audit)

**Trigger it yourself** (wait: ~1 min (repeat runs: wait out the 15-minute episode))

```bash
$K -n extorq-apps exec deploy/lab-portal -- id             # interactive exec by a human identity
# negative control: reading logs is not exec
$K -n extorq-apps logs deploy/lab-portal --tail=5 >/dev/null
```

**What you should see.** Alert naming the pod, container and the human user (system components and service accounts are excluded). The audit log shows that an exec session was opened, **not** what ran inside it.

**False positives considered:**

* Administrators debugging a workload. Handling: alerted by design (exec is privileged access to the container); sessions by one person in one pod merge into one alert per 15-minute episode, so a debugging session is one item to acknowledge.
* CI/CD or operations tooling that runs commands in pods with a personal or tool credential. Handling: the tool's exact authenticated identity can be listed in excluded_users after review. Kubernetes user names come from the credential (client certificate CN or OIDC claim), not from the request, so the exclusion is not something a caller can spoof without that credential; no prefixes or patterns are accepted.

**Blind spots (what this rule cannot see):**

* Exec by service accounts (for example a stolen pod token used for lateral movement) is excluded by design (system identities); K8S-002 covers granting pods/exec through RBAC.
* Exec through the kubelet API (port 10250) or the container runtime on the node bypasses the API server and is not audited.
* The executed command comes from the request URI and is redacted and bounded by the audit normaliser (attributes.exec_command); what the command did inside the container (stdin of an interactive shell) is never visible.
* Denied attempts (403), port-forward sessions and ephemeral debug containers (kubectl debug; K8S-001/K8S-005 when privileged) are not this rule.

### K8S-004: Cluster-wide secret enumeration

* **Rule** `K8S-004` v1.0.0, severity **high**, ATT&CK T1552.007, T1613, runs every 60 s (look-back 1800 s), dedup `window_bucket` (900 s buckets).
* **Telemetry it needs:** `k8s.audit` → `k8s.api.request`.

**Why it fires.** An identity that is not a control-plane component successfully listed or watched secrets across the whole cluster (kubectl get secrets -A: one request returns every secret), or listed secrets in at least three different namespaces within ten minutes (the same enumeration done namespace by namespace). Secrets hold service account tokens, registry credentials and application passwords, so cluster-wide access is credential access. Control-plane identities and kube-system service accounts are excluded; service accounts of workload namespaces are not, because a stolen workload token enumerating secrets is the main case. Only successful requests count. Confidence: high (the kube-apiserver audit record is authoritative for who received which secrets).

**Thresholds / parameters** (`params` in the rule YAML): `{"window_seconds":600,"min_namespaces":3,"allowed_identities":[]}`

**What the automated test does** (`detection_tests`, test id `kubernetes.k8s-004`)

* Positive: kubectl get secrets -A as the human admin identity (output discarded).
* Negative control (must NOT alert): kubectl get configmap kube-root-ca.crt in extorq-apps (one object, one namespace).
* Cleanup: Nothing to remove (reads only).
* Expected: K8S-004 on k8s:extorq-lab for the cluster-wide list of secrets.
* Why it is safe: kubectl's table output carries names and metadata only and is discarded at the OS level (never stored or printed); the audit policy logs secrets at Metadata level.
* Evidence source and wait: kube-apiserver audit log via the OTel DaemonSet (k8s.audit)

**Trigger it yourself** (wait: ~1 min (repeat runs: wait out the 15-minute episode))

```bash
$K get secrets -A -o name >/dev/null                        # cluster-wide enumeration (output discarded)
# negative control: one object, one namespace
$K -n extorq-apps get configmap kube-root-ca.crt >/dev/null
```

**What you should see.** Alert for a cluster-wide `list` of secrets by a non-system identity. Secret *values* never appear in the audit metadata or in ExtorQ.

**False positives considered:**

* Operators and controllers that legitimately watch all secrets (cert-manager, external-secrets, Velero, ingress controllers). Handling: their exact service account identity (system:serviceaccount:<namespace>:<name>) goes into allowed_identities after review. A service account identity is issued by the cluster for that namespace, so reusing it requires that namespace's token, not just a chosen name.
* An administrator running kubectl get secrets -A while troubleshooting. Handling: alerted by design (it exposes every credential of the cluster); one alert per person and 15-minute episode.
* Control-plane components (kube-controller-manager, the API server, kubelets) and kube-system controllers watch secrets continuously. Handling: excluded by identity prefix (system:* except workload service accounts, and system:serviceaccount:kube-system:*); those identities require control-plane credentials.

**Blind spots (what this rule cannot see):**

* Targeted reads of individual secrets by name (get), secrets read through pods that mount them (the kubelet fetches them), and access through etcd or node credentials.
* Denied attempts (403) are not alerted; they remain visible in the audit log and in the investigation context.
* A stolen kube-system service account token or a reviewed operator's token is excluded by design.
* Sweeps slower than three namespaces in ten minutes.

### K8S-005: Privileged pod admitted in a namespace without Pod Security enforcement

* **Rule** `K8S-005` v1.0.0, severity **high**, ATT&CK T1610, T1611, runs every 60 s (look-back 1800 s), dedup `window_bucket` (3600 s buckets).
* **Telemetry it needs:** `k8s.audit` → `k8s.api.request`; `k8s.api_inventory` → `k8s.resource.created`, `k8s.resource.updated`.

**Why it fires.** The API server admitted a pod (or an ephemeral debug container) that runs privileged, shares a host namespace (hostPID, hostNetwork, hostIPC), mounts a hostPath volume or adds a dangerous capability. Such a pod can reach the node and is the usual first step of a container escape. This happens in namespaces whose Pod Security level allows it (no enforcement, or privileged); K8S-001 covers the same request when it is denied. Platform pods are exempt only when BOTH the namespace is a configured platform namespace AND the creator is a kubelet or a kube-system controller. Confidence: high when the inventory's view of the same named pod carries the same kind of flag (two sources agree); medium for the audit record alone (always the case for controller-created pods, whose audit record has no pod name).

**Thresholds / parameters** (`params` in the rule YAML): `{"privileged_flags":["privileged","host_pid","host_network","host_ipc","host_path","host_path_root","dangerous_capabilities"],"platform_namespaces":["kube-system","local-path-storage","extorq-system"]}`

**What the automated test does** (`detection_tests`, test id `kubernetes.k8s-005`)

* Positive: Create namespace extorq-test-<id> without Pod Security labels, then a privileged pod in it: admitted (201).
* Negative control (must NOT alert): An unprivileged, restricted-compliant pod in the same namespace.
* Cleanup: Delete both pods, then the namespace; verify they are gone.
* Expected: K8S-005 on k8s:extorq-lab for the admitted privileged pod.
* Why it is safe: Both pods are pinned to a node that does not exist, so the scheduler never places them and the privileged container never runs.
* Evidence source and wait: kube-apiserver audit log via the OTel DaemonSet (k8s.audit)

**Trigger it yourself** (wait: ~1 min)

```bash
$K create namespace extorq-test-$ID                           # no Pod Security labels => nothing is enforced
cat <<EOF | $K create -f -        # ADMITTED (201): privileged pod, never scheduled
apiVersion: v1
kind: Pod
metadata: {name: extorq-test-$ID, namespace: extorq-test-$ID}
spec:
  automountServiceAccountToken: false
  restartPolicy: Never
  nodeSelector: {kubernetes.io/hostname: extorq-test-unscheduled}
  containers:
  - {name: worker, image: "alpine:3.19", command: ["sleep","300"], securityContext: {privileged: true}}
EOF
$K delete namespace extorq-test-$ID --wait=true             # cleanup (deletes the pod too)
```
Negative control: an unprivileged, restricted-compliant pod in the same namespace.

**What you should see.** Alert for the **admitted** privileged pod (the opposite case of K8S-001, where admission refused it).

**False positives considered:**

* Platform DaemonSets and static pods (kube-proxy, CNI, CSI drivers, log collectors) need host access. Handling: exempt only when the namespace is in platform_namespaces AND the creator is a kubelet (system:node:*) or a kube-system controller service account; both require control-plane credentials, and a person creating a privileged pod in the same namespace is still alerted.
* Node agents installed in another namespace (monitoring, security agents). Handling: add that namespace to platform_namespaces after reviewing who can write to it; controller-created pods there are then exempt, everything else still alerts.
* An administrator using kubectl debug node/<node> (a privileged pod with the host's namespaces and root filesystem). Handling: alerted by design; it is full node access.

**Blind spots (what this rule cannot see):**

* Workload templates (Deployment, DaemonSet) are audited at Metadata level, so the privileged spec is seen when the controller creates the pods; a privileged workload in a platform namespace created through its controller is exempt.
* Pods admitted while the audit pipeline was down, static pods placed directly in a node's manifest directory outside kube-system, and server-side dry runs (nothing is admitted).

```bash
cat > ~/Library/LaunchAgents/$L.plist <<EOF
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>$L</string>
  <key>ProgramArguments</key><array><string>/bin/sh</string><string>-c</string><string>/tmp/extorq-test-$ID</string></array>
  <key>RunAtLoad</key><false/>
</dict></plist>
EOF
rm -f ~/Library/LaunchAgents/$L.plist      # cleanup; never launchctl load
```
Negative control: the same plist running `/usr/bin/true` (raises MAC-001 only). The script path does not exist and the agent is never loaded.

**What you should see.** Alert for a launch item that starts a shell/interpreter or runs from a user-writable path; MAC-001 alerts too (documented overlap).

**False positives considered:**

* Vendor or developer agents that wrap their binary in /bin/sh -c or run a Python/Node script (some updaters, local development services). Handling: one alert per distinct plist content; after review the exact content digest can be allowlisted (allowlist_sha256). No label, path or program allowlist: all three are chosen by whoever writes the plist.
* Installers that stage files in /tmp and register a one-shot agent. Handling: reported; the temp_paths feature shows exactly which argument points to the shared location.

**Blind spots (what this rule cannot see):**

* Interpreters reached indirectly (a compiled wrapper binary that runs a script, an interpreter renamed to an unexpected basename) and user-writable locations other than the listed temporary and shared directories (for example hidden directories in the home).
* The script or binary content itself is not inspected; only the plist's program and arguments.
* Everything MAC-001 cannot see (other persistence mechanisms, items removed between scans).

### MAC-003: Listener exposed on all interfaces by a non-allowlisted process

* **Rule** `MAC-003` v1.0.0, severity **medium**, ATT&CK T1571, T1205, runs every 60 s (look-back 1800 s), dedup `window_bucket` (3600 s buckets).
* **Telemetry it needs:** `macos.inventory` → `network.listener.opened`.

**Why it fires.** A process on a macOS host started listening for TCP connections on all interfaces (0.0.0.0 or ::), so anything on every network the Mac joins can connect to it: a bind shell, a debugging server, a development tool started with --host 0.0.0.0. Loopback listeners and UDP sockets are out of scope (lsof reports every bound UDP client socket as a listener). Software that is supposed to listen on all interfaces is allowlisted by exact executable path; the defaults are Apple daemons in SIP-protected system locations. Confidence: high when lsof attributed the socket to an executable; medium when the owner is unknown (never allowlisted).

**Thresholds / parameters** (`params` in the rule YAML): `{"any_addresses":["0.0.0.0","::"],"allowlist_executables":["/usr/libexec/rapportd","/usr/libexec/sharingd","/System/Library/CoreServices/ControlCenter.app/Contents/MacOS/ControlCenter","/sbin/launchd"]}`

**What the automated test does** (`detection_tests`, test id `macos.mac-003`)

* Positive: A Python child process listens on 0.0.0.0:<free port 42000-48999>, accepting and closing connections, for up to 3 inventory cycles.
* Negative control (must NOT alert): The same listener bound to 127.0.0.1.
* Cleanup: Terminate the listener and verify the port is closed (it also exits by itself).
* Expected: MAC-003 on macos:workstation-01 naming the port and the process.
* Why it is safe: No data is served (connections are closed on accept); the process has a hard lifetime; the macOS firewall settings are not touched.
* Evidence source and wait: listening sockets in the host inventory (macos.inventory), up to 3 cycles

**Trigger it yourself** (wait: ~1 min)

```bash
PORT=$((42000 + RANDOM % 7000))
python3 - $PORT <<'PY' &
import socket, sys, time
s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("0.0.0.0", int(sys.argv[1]))); s.listen(5); s.settimeout(1); end = time.time() + 120
while time.time() < end:
    try: c, _ = s.accept(); c.close()
    except socket.timeout: pass
PY
LPID=$!; sleep 90; kill $LPID                 # cleanup: stop the listener
```
Negative control: the same listener bound to `127.0.0.1`.

**What you should see.** Alert naming the port and the process (`python3`), because a non-allowlisted executable listens on all interfaces. Needs the listener to exist for at least one inventory scan.

**False positives considered:**

* Apple services that listen on all interfaces by design (AirPlay Receiver on 5000/7000, Continuity). Handling: allowlisted by exact executable path in SIP-protected locations, where no other binary can take that path while System Integrity Protection is enabled (SIP status is reported by the posture collector). Never by process name, which any binary can claim.
* Developers starting a local server bound to 0.0.0.0 (npm run dev --host, python -m http.server). Handling: alerted by design: the server is reachable from the network. Repeated restarts of one tool on one port merge into one alert per hour; long-lived reviewed tools can be allowlisted by exact path.
* Third-party apps with LAN discovery or sync (Spotify, Dropbox, AnyDesk). Handling: exact executable path in allowlist_executables after review.

**Blind spots (what this rule cannot see):**

* UDP services (excluded as noise), listeners that exist for less than one scan interval (60 s), and sockets lsof cannot attribute (still alerted, medium).
* A malicious use of an allowlisted daemon (for example a socket-activated launchd job owned by /sbin/launchd): MAC-001/MAC-002 cover the launch item that requests the socket.
* Exposure through the macOS application firewall settings is not evaluated here.

### MAC-004: Burst of sudo authentication failures

* **Rule** `MAC-004` v1.0.0, severity **medium**, ATT&CK T1110.001, T1548.003, runs every 60 s (look-back 1800 s), dedup `window_bucket` (300 s buckets).
* **Telemetry it needs:** `macos.unified_log` → `auth.sudo.failure`, `auth.local.failure`, `auth.sudo.command`.

**Why it fires.** sudo on a macOS host rejected the password of one account at least three times within five minutes (one sudo invocation reports up to three attempts in its "N incorrect password attempts" line, so three single failures or one exhausted prompt both count). Password guessing against sudo is how a foothold with a user's session tries to become root. Authorisation denials (not in sudoers, command not allowed) and non-interactive sudo -n are not password guesses and are not counted. Confidence: high when opendirectoryd password-verification failures for the same account corroborate the burst (two subsystems agree); medium for sudo's log alone. The alert also reports whether the account ran sudo successfully afterwards.

**Thresholds / parameters** (`params` in the rule YAML): `{"window_seconds":300,"min_failed_attempts":3,"corroboration_seconds":60,"auth_failure_pattern":"(?i)incorrect password attempt|authentication failure"}`

**What the automated test does** (`detection_tests`, test id `macos.mac-004`)

* Positive: sudo -k, then three `sudo -k -S -v` calls, each with a random wrong password.
* Negative control (must NOT alert): A single `sudo -k -S -v` call with a random wrong password.
* Cleanup: sudo -k (invalidate any cached sudo timestamp).
* Expected: MAC-004 on macos:workstation-01 for the current user.
* Why it is safe: No privilege is obtained: passwords are random; cached credentials are ignored; the test refuses to run with Touch ID for sudo and stops if sudo ever accepts. Four failed attempts per run: do not run it where an account lockout policy is lower.
* Evidence source and wait: sudo records in the unified log (macos.unified_log)

**Trigger it yourself** (wait: ~1 min)

```bash
sudo -k
for i in 1 2 3; do echo "wrong-$RANDOM" | sudo -k -S -v 2>/dev/null; done   # three wrong passwords; no privilege is ever obtained
sudo -k                                                                      # cleanup: drop any cached timestamp
```
Negative control: a single failed attempt (below the threshold). You will not be prompted: `-S` reads the (wrong) password from the pipe.

**What you should see.** Alert for the current user: three `auth.sudo.failure` events from the unified log within the rule window.

**False positives considered:**

* A person mistyping the sudo password three times. Handling: the threshold is sudo's own limit (three attempts) inside five minutes; sudo_success_after shows that the same account succeeded right afterwards, the typical typo pattern, so the alert can be closed quickly. No account allowlist (the guessed account is the target, not the attacker).
* Scripts that call sudo with a stale or wrong password on stdin. Handling: reported; the ttys feature shows that no terminal was involved.

**Blind spots (what this rule cannot see):**

* Guessing slower than three attempts per five minutes, and password checks outside sudo (screen unlock, authorization prompts) that are not sudo failures.
* sudo configured with a cached timestamp or NOPASSWD rules never asks for a password and therefore never fails.
* Unified-log records the collector missed (log rotation before collection is a gap event).

### MAC-005: Unsigned application installed

* **Rule** `MAC-005` v1.0.0, severity **medium**, ATT&CK T1204.002, T1553.001, runs every 60 s (look-back 3600 s), dedup `event`.
* **Telemetry it needs:** `macos.inventory` → `software.installed`.

**Why it fires.** An application bundle without a valid identity-bearing code signature appeared in /Applications or ~/Applications: unsigned, tampered (the signature no longer verifies) or ad-hoc signed (signed without any identity, which is how unsigned arm64 code is made runnable). Legitimate macOS software is signed by Apple or an identified developer; trojanised apps and loaders often are not, and Gatekeeper only prompts when the quarantine attribute is present. The collector verifies the signature of new bundles; an undetermined verdict never alerts. No allowlist: such a bundle has no verifiable identity. Confidence: high when the bundle identifier was read together with the verdict; medium when the bundle carries no readable identity.

**What the automated test does** (`detection_tests`, test id `macos.mac-005`)

* Positive: Create the minimal unsigned bundle '/Applications/ExtorQ Test.app' (Info.plist and a two-line shell script as executable); it is never executed.
* Negative control (must NOT alert): Copy a small signed third-party app to '/Applications/ExtorQ Test Signed Copy.app' (signature verified intact).
* Cleanup: Delete both bundles after verifying their bundle identifiers.
* Expected: MAC-005 on macos:workstation-01 for the unsigned bundle.
* Why it is safe: Nothing is executed; no sudo (admin users may write /Applications).
* Evidence source and wait: application bundle scan with code-signature check (macos.inventory)

**Trigger it yourself** (wait: ~1 min)

```bash
A="/Applications/ExtorQ Test.app"; mkdir -p "$A/Contents/MacOS"
cat > "$A/Contents/Info.plist" <<EOF
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>CFBundleIdentifier</key><string>com.extorq.test.$ID</string>
  <key>CFBundleName</key><string>ExtorQ Test</string>
  <key>CFBundleExecutable</key><string>extorq-test</string>
  <key>CFBundlePackageType</key><string>APPL</string>
  <key>CFBundleShortVersionString</key><string>1.0.0</string>
</dict></plist>
EOF
printf '#!/bin/sh\nexit 0\n' > "$A/Contents/MacOS/extorq-test"; chmod +x "$A/Contents/MacOS/extorq-test"
codesign --verify --strict "$A" || echo "unsigned (expected)"
rm -rf "$A"                                            # cleanup; the app is never executed
```
Negative control: copy a small **signed third-party** app (not an Apple system app: SIP forbids copying those) under another name and delete it afterwards.

**What you should see.** Alert naming the bundle path, with `signed=false`. Installation and execution are different things; nothing here runs.

**False positives considered:**

* Open-source or in-house tools distributed without a Developer ID signature, and apps built locally (Xcode "Sign to Run Locally" is ad-hoc) and copied to /Applications. Handling: alerted by design; each install of a version is one alert. No bundle-id, name or path allowlist because all three are written by the bundle's author; the durable fix is to sign in-house builds.
* A bundle still being copied fails verification. Handling: the collector reports a new bundle only after it has been quiet for settle_seconds and re-checks a just-settled failure on the next scan, so a half-copied bundle is not reported as unsigned.
* Apps whose signature breaks because they modify their own bundle (some self-updaters). Handling: reported; a broken signature is also what tampering looks like, so it is reviewed rather than suppressed.

**Blind spots (what this rule cannot see):**

* Bundles outside the inventoried application directories (Downloads, /tmp, external volumes), command-line binaries, and apps that are run without being copied anywhere.
* An undetermined signature check (timeout, unreadable bundle) is never alerted: unknown is not treated as unsigned.
* Notarisation and the quarantine attribute are not evaluated (spctl --assess may contact Apple); a validly signed but malicious app is out of scope.
* Ad-hoc signatures are recognised only when the collector reports signature_type; without it only explicitly unsigned or invalid bundles alert.
