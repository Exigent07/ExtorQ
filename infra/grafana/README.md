# ExtorQ Grafana (owner: D1)

Analytics dashboards over the ExtorQ ClickHouse store, provisioned as code. The analyst
console is the place to triage and investigate; Grafana is for trends, health and
ad-hoc drill-down with a read-only identity.

| Item | Value |
|---|---|
| Compose service | `grafana` (profile `full`), built from this directory |
| URL | http://127.0.0.1:3001 (loopback only), user `admin` |
| Image | `extorq/grafana:0.1.0`, `FROM grafana/grafana:13.1.10@sha256:467fa061…` |
| Plugin | `grafana-clickhouse-datasource` 4.23.5, installed at **build** time |
| Datasource | uid `extorq-clickhouse`, ClickHouse user `extorq_grafana`, HTTP `clickhouse:8123` |
| Dashboards | folder **ExtorQ** (uid `extorq`), generated by `generate_dashboards.py` |

## Files

| Path | Purpose |
|---|---|
| `Dockerfile` | pinned base, plugin install into a root-owned directory, provisioning, hardening ENV, healthcheck |
| `provisioning/datasources/extorq-clickhouse.yaml` | datasource (not editable from the UI) |
| `provisioning/dashboards/extorq.yaml` | file provider: folder ExtorQ, UI saves and deletion disabled |
| `dashboards/*.json` | provisioned dashboards (generated; do not edit by hand) |
| `generate_dashboards.py` | single source of every panel and its SQL |

## Build, run, update

```bash
uv run python infra/grafana/generate_dashboards.py          # after editing panels
uv run python infra/grafana/generate_dashboards.py --check  # CI-style freshness check
docker compose --profile full build grafana
docker compose --profile full up -d --no-deps grafana       # does not touch other services
```

The datasource and dashboards are re-read from the image at every start; dashboard JSON is
baked into the image, so a rebuild is needed after regenerating.

Panel clarity rules (also enforced by the unit test): every description says what the panel
shows, where the data comes from (`Source:` / `Sources:` with the table or view and the
telemetry source) and its caveats; durations carry `s`/`ms` units; volume stats are neutral
while alert and open-finding stats turn orange above zero; lag, backlog and queue-age charts
draw dashed thresholds; state columns are coloured by meaning (`VALUE_COLOURS`: severity,
health, freshness, rule status, coverage, finding state, analyst status, risk flags, code
signature, listener exposure); cross-asset tables show the inventory name (`v_assets.name`)
with the asset id as the last column, and per-class dashboards name the host or repository
by the natural name inside the asset id (`linux:lab-vm-01` -> `lab-vm-01`). Unknown booleans
(for example an unreported code signature) are shown as `unknown` / `not reported`, never as
`no`. No panel names the storage dropped by migration 0008 (`simulation_run_id`,
`scenario_id`, `simulation_run_ids`, `simulation_runs`).

Query rules (enforced by `tests/unit/api/test_grafana_dashboards.py`):

* Explicit columns only; never `SELECT *`, never `events.raw`/`events.payload` or
  `ingest_quarantine.payload_excerpt` (the identity cannot read them anyway).
* Duplicate-safe: `uniqExact(...)`, `LIMIT 1 BY event_id`/`GROUP BY event_id`, and the
  `FINAL` views (`v_alerts`, `v_services`, `v_findings_current`, ...). Never `count()` on events.
* Every query over an append-only/versioned table is bounded with `$__timeFilter(...)`.
  "Current state" panels read latest-state views and say so in their description.
* No dashboard variables: no stored value is ever interpolated into SQL text.
* No aggregate alias may shadow a column (ClickHouse aliases are query-global).

Service coverage in dashboards is an approximation computed in SQL from `v_services`
(reported status; a discovery record older than 1 h shows as `degraded (stale record)`).
The console/API additionally checks collector staleness per telemetry source
(`docs/api/README.md`, "Service coverage").

## Security configuration

| Control | How |
|---|---|
| Least-privilege data access | `extorq_grafana`: `readonly=2` profile with caps + quota; SELECT on analytics tables, column grant on `events` without `raw`/`payload`, quarantine without `payload_excerpt`; no access to `analyst_actions`, `investigation_contexts` |
| Datasource locked | provisioned with `editable: false` |
| Datasource secret | `secureJsonData.password: $__file{/run/secrets/extorq_grafana_password}`: read from the compose file secret at provisioning, stored encrypted in Grafana's DB, never in env, image or repo |
| Secret encryption key | `GF_SECURITY_SECRET_KEY__FILE=/run/secrets/grafana_secret_key` uses the per-deployment key generated by bootstrap |
| Admin password | `GF_SECURITY_ADMIN_PASSWORD__FILE=/run/secrets/grafana_admin_password` (compose) |
| No anonymous access / sign-up / org creation | `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_USERS_ALLOW_SIGN_UP=false`, `GF_USERS_ALLOW_ORG_CREATE=false` |
| Clickjacking / cookies | `GF_SECURITY_ALLOW_EMBEDDING=false` (X-Frame-Options deny), `GF_SECURITY_COOKIE_SAMESITE=strict`, CSP enabled, sessions 8 h inactive / 24 h max |
| No outbound calls | gravatar, usage reporting, update checks, news feed, feedback links, external snapshots, public dashboards, plugin preinstall, plugin admin and signing-key retrieval disabled |
| No runtime plugin downloads | plugin baked at build (`grafana cli` verifies the grafana.com checksum); Grafana verifies the Grafana Labs signature on load (`signature: valid`) |
| Container | uid 472, read-only root filesystem, `cap_drop: ALL`, `no-new-privileges`, port bound to 127.0.0.1 (compose) |
| Read-only content | plugin, provisioning and dashboard files are root-owned and not writable by the server |
| Grafana alerting | disabled (`GF_UNIFIED_ALERTING_ENABLED=false`): ExtorQ alerts come only from the detector |

## Verification

| Command | Proves |
|---|---|
| `uv run pytest tests/unit/api/test_grafana_dashboards.py -q` | generated JSON is current; every panel follows the query and clarity rules (sources named, units, thresholds, names, no dropped storage or removed wording); provisioning and Dockerfile settings |
| `uv run pytest tests/integration/api/test_grafana_sql_clickhouse.py -m integration -q` | every panel query runs on a throwaway ClickHouse with the current migrations as the real `extorq_grafana` role (synthetic rows) and returns the expected, duplicate-safe results, including the asset-name joins |
| `uv run pytest tests/integration/api/test_grafana_live.py -m integration -q` | against the running Grafana: datasource health, plugin version/signature, provisioning, every panel query through `/api/ds/query` as `extorq_grafana`, denied privileged reads/writes, effective hardening settings |

## Known limitations

* The hop Grafana -> ClickHouse is plain HTTP on the internal `data` network (no egress,
  never published); ClickHouse TLS is not configured in this single-host stack.
* The official image's `__FILE` mechanism exports the admin password into the server
  process environment (readable only by the same non-root user inside the container). The
  admin password is applied when the Grafana database is first created; rotating the
  secret later requires `grafana cli admin reset-admin-password` (or a fresh
  `grafana-data` volume).
* `cookie_secure` is off because Grafana is served over plain HTTP on loopback.
